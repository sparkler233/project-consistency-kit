# 文档整理

<!-- 一致性机制 version: 2026-09-25 -->

用户明确要求整理文档、接入或升级项目需要确定文档布局时读取。日常 wrapup 不加载本文件。整理复用 wrapup 的计划、一次确认、执行核对与提交流程，不另跑一套。

## 目的

保持项目文档健康，让一致性机制稳定运行——机制靠 PROJECT 入口、联动目录、决策记录这些文档运转。具体看三个方面：

1. **准确**：文档说的和项目实际一致，彼此不矛盾，状态不过时。
2. **好找好懂**：人或新会话的 AI 从 PROJECT 入口出发，能很快找到并理解需要的信息；入口写出各位置的具体主题，链接有效，没有无人引用的文件，联动目录与实际相符。
3. **精简合适**：不重复，不堆积已结束的过程，也不拆得过碎；结构随项目发展调整。

## 范围

可以动项目自己的各类文档：修改、改写、移动、合并、拆分、删除、建立关联。

不动：

- 安装器装进来的机制文件(Skill、脚本、hook、运行规则)。联动目录的内容是项目自己的联动规则，可以整理。
- 代码、数据、二进制；实验等原始证据的内容。
- `PROJECT.md`「待提交」与「最近决策」，它们由 wrapup 的决策脚本维护。

`AGENTS.md` 可以整理结构和措辞，不改变规则的意思。

## 底线

- 看到问题就大胆提出来，觉得是问题都可以提；动手时不激进也不保守，拿不准的交给用户决定。
- 删除必须经用户确认。直接删掉内容、或改写时去掉了原有的意思和限定，都算删除，要在计划中标明删什么、为什么，以及原文是移入其他位置、逐字写入本次提交正文，还是不再保留。
- 移动内容时先写好新位置并核对，再删旧位置、修引用。

## 交付

计划用编号列出发现的问题，每条写：属于哪个方面(准确 / 好找好懂 / 精简合适)、问题是什么、建议怎么改(标出其中的删除)、会影响哪些文件或引用。用户可以全部批准，也可以按编号取舍。计划同时给出拟提交文件与提交说明全文，按 wrapup 的一次确认执行。

整理单独提交。有日常工作要收尾时，先完成日常 wrapup 的提交，再整理并另行提交，使一次提交只做一类事，也便于单独撤销。
