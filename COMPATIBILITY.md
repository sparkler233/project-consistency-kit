# Compatibility

Applies to Recensio 2.x (from 2.0.0).

Within 2.x there are three tiers. **Stable** parts stay compatible: any change must keep reading the old format or come with a migration. **Experimental** parts may change; see "Experimental scope" below. **Not promised** covers the kit's internal interfaces, which change together within one version. "Stable" is a release policy, not a guarantee about how reliably a model behaves.

| Stable | What is fixed |
| --- | --- |
| Files and their roles | `PROJECT.md`, `AGENTS.md`, `CLAUDE.md` containing only `@AGENTS.md`, `一致性机制/运行规则.md` (runtime rules), the project-owned `一致性机制/文件联动目录.md` (linkage rules), `一致性机制/VERSION` |
| The parts of `PROJECT.md` that scripts read | The two subsections `### 待提交` (pending) and `### 最近决策` (recent decisions). A pending entry starts with `- date · 决策 N:title` followed by indented items; recent decisions are one line each, generated by a script. Other sections, headings and layout are not fixed |
| Decision history | The `决策 N · date · title` line in commit messages, and the trailers `Decision:`, `Decision-Archive:`, `Supersedes:` and `Adjusts: old by new`. History already written stays searchable |
| Linkage rules | Each rule is a heading followed by 「触发」 (trigger) and 「动作」 (action). Paths in backticks in the trigger (including directories and `*`) are matched by a script; everything else is left to the model |
| How you start things | catchup and wrapup (Claude Code `/catchup` `/wrapup`, Codex `$catchup` `$wrapup`); saying 「收尾」 means wrapup; the installer entry `/引入一致性机制` and the installer skill |
| Key behaviour | catchup is read-only; on the main branch wrapup commits locally after you confirm and never pushes; the last-wrapup pointer only moves on the main branch after checks pass; with no reliable baseline, nothing is guessed |
| Local Git state | The last-wrapup pointer `refs/pck/synced`; the main-branch setting `projectConsistency.canonicalBranch` |
| Hook wiring | Two hooks: the per-turn note (UserPromptSubmit) and the post-compaction reminder (SessionStart). Claude Code uses `.claude/settings.json`, Codex uses `.codex/hooks.json`, Windows goes through `run-hook.ps1`. Upgrades keep your other hooks |
| Commands for users | The fetch script `fetch-kit.sh` / `.ps1` with `--release TAG\|latest`, `--cache-dir`, `--offline`, `--verify-dir`; the hook self-check `node .agents/hooks/selfcheck.mjs` |
| Version identity | `VERSION` holds the SemVer version, kept separate from the revision date; the release asset names and checks the fetch script relies on do not change silently |

**Not promised:** the command-line options and JSON fields of scripts such as `scope`, `decisions`, `synced-guard`, `startup-check` and `linkage`. You can call them, but they are not a stable interface; what fields such as `base` and `can_advance` mean, including their safety meaning, will not be quietly changed. The wording, steps and report formats of the runtime rules and skills, hook messages, the internal layout of the distribution package and other metadata fields are not fixed either. Mixing mechanism files from different versions is not supported.

## Experimental scope

The workflow and interfaces of experimental features may change incompatibly within 2.x. Any such change must explain how to migrate and how unfinished tasks carry on, and must still protect existing work, history and other worktrees without going beyond what you have allowed.

| Area | Status |
| --- | --- |
| Parallel work: starting, syncing, merging and closing tasks, task checkpoints and notes about related changes | Available as experimental. Broader awareness of in-progress changes on other branches is still being explored |
| Save reminders based on context usage | Internal trial only, not shipped |
| Communication and automatic coordination between sessions | Research direction with experimental material, not a feature |
| The agent finishing a save by hand when the scripts cannot recover | Not implemented; a possible future experiment. Taking over Git operations by hand is not allowed today |

Parallel work covers: the `start / sync / land / close` commands of `task.mjs` and their options, the merge-into-main-line flow, how task checkpoints are written and found (`Task:`, `Land-Checked:`, and the goal / progress / remaining lines), branch information in the overview, the per-turn note policy, and switching between single-session and parallel work (a future direction, not yet implemented). These live in several files and are not split by whole file; stable capabilities in the same script still follow the stable list above. Old checkpoints remain recoverable through compatible reading or an explicit migration. Several sessions in one worktree, automatic orchestration across sessions and lossless recovery after compaction are not promised.

Startup checks, post-compaction feedback and file linkage are not experimental as a whole; their test coverage and known limits are described separately. Listing a direction as experimental does not mean it is available, and does not permit anything the current rules forbid.
