# 从 v1.3.0 升级

<!-- 一致性机制 version: 2026-10-02 -->

目标 `一致性机制/VERSION` 为 1.3.0 时读取。机制件照安装器步骤 5 更新；本细则只管 v1.3.0 留下、需要按新结构改造的项目文件。改造由你按下面的目的与底线完成，不照搬固定写法。各项改造计划并入安装器步骤 3 的总计划一起确认。

## 改造后应达到的状态

- `PROJECT.md` 是入口式，结构同套件 `templates/PROJECT.md`：目标与边界、总体状态、阅读入口(写出各位置的具体主题与何时读)、关键决策(「待提交」「最近决策」)。
- `AGENTS.md` 只剩项目自己的规则，加上新模板的接入块(`<!-- 一致性机制:接入 begin ... -->`，引用运行规则，并给出压缩后指令)。
- `一致性机制/运行规则.md` 已安装；机制规则只在这里。`一致性机制/机制设计说明.md` 与 `一致性机制/README.md` 已按用户确认删除。
- `一致性机制/文件联动目录.md` 是新模板结构，保留项目自己的联动关系。
- 决策档案已写入升级提交正文并删除，或按用户选择保留为只读旧历史。

## 底线

- 删除须经用户确认。直接删掉内容、或改写时去掉了原有的意思和限定，都算删除；计划中写明删什么、为什么，以及原文是移入其他位置、逐字写入升级提交正文，还是不再保留。整段改写或合并的章节，计划按旧章节逐项列出这些去向，不只写“改写为新结构”。
- 项目自己写的内容不丢：只有能确认来自 v1.3.0 模板的机制条款，才按下文删除；拿不准来源的，列给用户决定。
- 移动内容时先写好新位置并核对，再删旧位置、修引用。
- 改造 PROJECT 时，按套件 `.agents/skills/wrapup/references/document-maintenance.md` 的目的判断什么该留在入口、什么该移到主题文档。

## AGENTS.md

v1.3.0 模板在同步纪律块外带来了以下条款(「工作约定」下，粗体开头)。它们在新版中由运行规则或 Skill 承担，与模板原文一致、或只有措辞差异时删除；改写过并含项目特有内容的，展示给用户决定：

- **三层分离**(README / PROJECT / AGENTS 分工)
- **Claude 适配**(CLAUDE 只含 `@AGENTS.md`)
- **工作流正本**(catchup / wrapup 只维护在 `.agents/skills/`)
- **宿主接线**(收尾提醒逻辑只在 `.agents/hooks/wrapup-reminder.mjs`)
- **套件身份**(`一致性机制/VERSION` 的含义)
- **重大决策**(在“关键决策记录”追加一行)

v1.3.0 的同步纪律块(`<!-- 一致性机制:同步纪律 begin ... -->` 到 `end`)整块换成新模板的接入块(marker 改为 `一致性机制:接入`)，不留旧块。块内有项目自加的内容时，在计划中逐句列出，移到块外保留。

项目自己的条款原样保留，不借升级改写。

## PROJECT.md

v1.3.0 模板的五节与新结构的对应：

| v1.3.0 | 新结构 |
| --- | --- |
| 一、项目背景 | 目标与边界 |
| 二、工作流程与里程碑 | 总体状态写当前所处阶段；流程细节与已结束的里程碑移到主题文档，或逐字写入升级提交正文 |
| 三、项目地图 | 阅读入口：每个位置写出负责什么、有哪些具体主题、何时读 |
| 四、当前阶段 | 总体状态 |
| 五、关键决策记录 | 关键决策 →「最近决策」 |

- 旧的决策记录行原样移入「最近决策」，不改写、不补全文；超过 10 条也先全部保留，之后第一次迁出决策的 wrapup 由决策脚本删除最老的行，并把没有全文的旧行逐字写入那次提交正文。
- 「待提交」写“(暂无)”。
- 项目在模板之外自加的章节，按内容归到入口、主题文档或 AGENTS；归不了的列给用户。
- 已有主题文档承载的细节，PROJECT 只留指针，不复述。

## 文件联动目录

v1.3.0 模板的“怎么用这份目录”、Part A 中 `PROJECT.md` / `AGENTS.md` / `文件联动目录.md` / `机制设计说明.md` 四行、Part B 通用规则 1–8，与模板原文一致的删除，改成新模板的结构(关键资料的受影响条件 / 项目联动关系 / 套件升级边界)。其中：

- 规则 2(决策落地)、规则 6(轮转归档)、规则 7(Claude 适配)、规则 8(套件版本)已由运行规则、wrapup 与安装器承担。
- 规则 4、5(外来二进制、素材目录 manifest)：项目实际有二进制素材时，改写为项目联动关系保留；否则删除。
- Part A 中项目登记的中枢，放进“关键资料的受影响条件”表；项目自定规则区的规则，放进“项目联动关系”，每条保持或改成模板的「小标题 + 触发 + 动作」写法，触发中能对应到文件或目录的写成反引号路径；只改写法，不改规则含义。

## 决策档案

用户同意删除时：

1. 引用前先检查下面两条已知的套件历史泄漏行(逐字相同才算)，命中时展示并询问是否剔除：
   ```text
   - 2026-06-11:启用套件级统一版本行与 CHANGELOG 治理(决策 9)
   - 2026-06-12:加入 Stop 收尾提醒与决策记录轮转归档(决策 10/11)
   ```
2. 升级提交正文逐字引用档案的全部记录行，trailer 段加 `Decision-Archive: <编号范围>`(如 `3-27`)。
3. 删除 `一致性机制/决策档案.md`，PROJECT 与联动目录中不再提到它。

用户不同意删除时：保留文件，在文件开头说明它是只读旧历史、不再写入；PROJECT 阅读入口加一行指向它。

## 旧机制文档

v1.3.0 装进项目的 `一致性机制/机制设计说明.md` 与 `一致性机制/README.md` 新版不再分发,设计理由改由套件仓库提供。它们是安装器管理的机制文件,列入删除计划,经用户确认后删除;项目改过其中内容时,先展示差异,由用户决定改动放到哪里。

## 升级提交

机制件与上述改造全部写入并按安装器步骤 8 验证后，按步骤 5 最后写入 `一致性机制/VERSION`，再准备一次升级提交：

- 标题说明从 v1.3.0 升级到新版本，以及 PROJECT 改为入口式等主要变化；
- 正文列出改造摘要，并逐字写入按计划要写入提交正文的原文(PROJECT 移出的内容、决策档案)；
- 把提交说明写成 UTF-8 文件，用 `git commit -F <文件>` 提交，不经 shell 管道拼接；
- 提交前向用户展示拟提交文件(用文字标明状态)与提交说明全文，确认后才提交。

安装器不推进 `synced`；之后第一次 wrapup 从原有 `synced` 起检查，升级提交也在检查范围内。

## preview.4 起的 Stop 退役

升级到 preview.4 或之后的版本,先更新机器级安装器,再按安装器 Skill 的「升级时退役旧 Stop hook」移除机制旧接线与三个旧脚本,保留用户其他 Stop hook。旧版接线描述仅用于识别迁移来源。

## 收尾指针迁移

preview.4 起使用 `refs/pck/synced`,兼容读取旧 `refs/tags/synced`。安装计划应包含 guard `migrate`:在主线上按已确认授权执行,只迁移已有位置,不推进检查边界,不提交工作区改动。新旧值不同时暂停,不得猜测。相关 worktree 的旧机制也须升级,否则旧脚本会继续写旧标签;远端标签不自动清理。
