# Recensio · 文件联动目录

<!-- 一致性机制 version: 2026-10-03 -->

> 本文件是**套件仓库自身的真实联动规则**,不再兼任新项目骨架。
> 分发骨架见 [`templates/一致性机制/文件联动目录.md`](../templates/一致性机制/文件联动目录.md);wrapup Skill 在每个目标项目里读取其根 `一致性机制/文件联动目录.md`。

## 使用方式

wrapup 对自 `synced` 以来的每个变化:

1. 检查 Part A 中枢文档是否受影响;
2. 检查 Part B 稳定联动规则;
3. 两者都没命中时临场判断隐性联动;
4. 新发现的稳定关系补进 Part B。

## Part A · 套件中枢文档

| 中枢文档 | 它应随什么改动而更新 |
|----------|--------------------|
| `PROJECT.md` | 套件背景、范围、流程、里程碑、项目地图、当前阶段或决策变化 |
| `AGENTS.md` | Agent 工作约定、权限边界、发版纪律或接入块变化 |
| `README.md` | 面向 GitHub 用户的能力、安装方式、使用流程或公开边界变化 |
| `一致性机制/运行规则.md` | 机制运行规则变化(本仓库与用户项目同一份,决策 73) |
| `一致性机制/机制设计说明.md`、`一致性机制/README.md` | 机制架构、真实行为、设计取舍或机制文件组成变化(只在本仓库,决策 77) |
| `一致性机制/文件联动目录.md` | 出现新的稳定联动关系 |
| `初始化新项目.md` | 绿地分发内容、文件布局或开张步骤变化 |
| `skills/project-consistency-installer/` | GitHub 获取、增量安装、升级、迁移或模板来源变化 |
| `distribution/manifest.txt` | 干净分发包文件边界变化 |
| `distribution/public-paths.txt` | GitHub 公开范围变化,或新增顶层文件、`docs/` 公开文档(决策 78) |
| `scripts/build-distribution.sh`、`scripts/verify-distribution.sh` | 发布包构建、来源记录、完整性或污染规则变化 |
| `.github/workflows/distribution.yml` | CI 验证、版本标签或 GitHub Release 行为变化 |
| `CHANGELOG.md` | 任何机制文件发生真实变化或形成新发布 |
| `ROADMAP.md` | 决策实现、改变或否定了其中某个方向;PROJECT 阅读入口中它的主题摘要随之更新(决策 67) |
| `一致性机制/VERSION` | 正式 SemVer、Release 标签、安装器 metadata 或分发版本身份变化 |

## Part B · 套件稳定联动规则

### 规则 1 · 机制件变化 → 版本、设计、索引与发布记录

**触发**:`.agents/skills/`、`.agents/hooks/`、`skills/project-consistency-installer/`、`.claude/commands/`、`.claude/settings.json`、`.codex/hooks.json`、`distribution/`、`.github/workflows/distribution.yml`、`scripts/`、`一致性机制/VERSION`、`一致性机制/hooks/`、`一致性机制/运行规则.md`、`templates/` 或本仓库的机制设计说明、机制 README 发生真实变化。
**动作**:
- 判断正式 SemVer 应升 major / minor / patch,保持 `一致性机制/VERSION` 与安装器 Skill metadata 一致;
- 全部机制文件的 `一致性机制 version:` 行统一推进到当天;
- `AGENTS.md` 与 `templates/AGENTS.md` 的接入块(`一致性机制:接入`)version 同步推进;
- 更新 `CHANGELOG.md`;
- 检查 `机制设计说明.md`、`一致性机制/README.md`、公开 `README.md` 是否需要联动。

### 规则 2 · B 类决策落地 → PROJECT

**触发**:safety net 捕获到对话中的决策。
**动作**(决策 46 / 47;wrapup 由 `decisions.mjs` 执行迁出、删行与核对,决策 63):拍板时全文写入 `PROJECT.md`「待提交」区(见 `一致性机制/运行规则.md` 第一节);写前按编号与摘要防重复;操作性内容同时改写到对应主题文档并标注 `(决策 N)`。wrapup 时:
- 全文移入提交正文;主题行带 `〔决策 N〕`(多条写作 `〔决策 45/46〕`);正文末尾每条决策一行 `Decision: N`,推翻旧决策时加 `Supersedes: M`;
- 清空「待提交」区,「最近决策」由脚本按 git 历史整段生成(决策 81、88):被 `Supersedes:` 推翻的不再出现,`Adjusts:` 生成“(部分被决策 N 调整)”;决策 44 及以前的旧行按规则 6 移出。

### 规则 3 · 套件结构或入口变化 → PROJECT

**触发**:顶层目录、关键文件、命令入口、模板位置或当前阶段变化。
**动作**:更新 `PROJECT.md`“阅读入口”或“总体状态”;只写指针与一两行现状,不复述主题文档内容。只有对外能力、安装或使用方式受影响时才更新 README。

### 规则 4 · 收到外来二进制 → 写 Markdown 摘要

**触发**:仓库出现外来的 `.docx`、`.pdf` 或其他无法文本 diff 的二进制。
**动作**:在同目录写 `.md` 摘要;原件按二进制策略处理。

### 规则 5 · 素材 / 大文件目录变化 → manifest 对账

**触发(条件)**:本轮改动落在含二进制的素材 / 大文件目录,或 LFS 指针变化。
**动作**:对账 `_manifest.md`,只维护用途 / 来源 / 授权或版权(视觉项目可加风格基准);纯文字同步跳过。

### 规则 6 · 最近决策超限 → 挤出最老的行

**触发(条件)**:PROJECT「最近决策」超过 10 条。
**动作**(决策 48、81;由 `decisions.mjs` 执行):「最近决策」按 git 生成,只留最近 10 条,不再归档——决策 45 起的全文与索引已在 git(`git log --grep='^Decision:'`)。决策 44 及以前的旧行删除前逐字写入该次提交正文,并加 `Decision-Archive: <编号>`。本仓库已无 `一致性机制/决策档案.md`,其原有记录见 `git log --grep='^Decision-Archive:'`。

### 规则 7 · Agent 指令、运行规则或适配入口变化 → 双宿主与模板对齐

**触发**:`AGENTS.md`、`CLAUDE.md`、`一致性机制/运行规则.md` 或 `templates/AGENTS.md` 变化。
**动作**:
- 机制运行规则只写在 `一致性机制/运行规则.md`,它就是分发给用户项目的那一份(决策 73);`AGENTS.md` 只保留接入块(一行引用与压缩后指令,不用 `@`,决策 58)与本仓库(套件源仓库)特有的开发规则,二者不得重复同一规则。运行规则只能写任何项目都适用的内容,不写本仓库特有规则、本仓库的决策编号(决策 74)或人与 AI 的分工;
- `templates/AGENTS.md` 的接入块与本仓库 AGENTS 的接入块内容一致;
- 运行规则只写机制是什么、文件、随时生效的规则、何时用 catchup / wrapup 与如何维护机制,不写 Skill 步骤、内容归属与设计理由;
- 确认根 `AGENTS.md` 是实体文件;
- 确认根 `CLAUDE.md` 是只含 `@AGENTS.md` 的普通文件导入适配器;
- 接入块或通用规则变化时同步更新 `templates/AGENTS.md`;
- 检查 catchup Skill 是否仍避免重复读取 harness 指令文件。

### 规则 8 · 分发模板变化 → 初始化、安装器与公开说明

**触发**:`templates/` 下文件新增、删除、改名或内容结构变化。
**动作**:
- 对齐 `初始化新项目.md` 的复制 / 排除步骤;
- 对齐 `project-consistency-installer` 的模板定位、新建与升级逻辑;
- 对齐 `PROJECT.md` 项目地图、公开 README 仓库结构和 `一致性机制/README.md`;
- 验证模板不含套件专属状态,套件真实联动规则、决策历史与 Release 来源 / 校验元数据不泄漏到目标项目。

### 规则 9 · README 只承载公开契约

**触发**:内部目录、阶段或决策变化。
**动作**:默认只更新 `PROJECT.md`;README 仅当公开能力、安装、使用方式或用户可见边界变化时联动,不得重新承担运行时项目地图职责。

### 规则 10 · 工作流 Skill 变化 → 宿主适配与分发对齐

**触发**:`.agents/skills/catchup/` 或 `.agents/skills/wrapup/` 变化。
**动作**:
- 保持 Skill 为唯一行为正本,`.claude/commands/catchup.md` 与 `wrapup.md` 只做薄适配,不得复制流程;
- 对齐增量安装器、绿地初始化、PROJECT 地图、公开 README 与机制索引;
- 校验两个 Skill 的 `SKILL.md`、`agents/openai.yaml` 与随附 scripts,并验证仓库级发现路径;catchup / wrapup 的 branch 基线和自动 `synced` 状态迁移只委托 wrapup guard,不得复制判断。
- 随附脚本变化时运行 `node scripts/test-wrapup-scripts.mjs`,涉及启动静态检查时另跑 `node scripts/test-startup-check.mjs`,以及并行相关的 `test-task.mjs`、`test-parallel.mjs`、`test-task-state.mjs`、`test-recent-decisions.mjs`;行为变化时补测试。
- 分发文件(Skill、脚本、整理细则、模板、运行规则、安装器)不写本仓库的决策编号,决策理由写在机制设计说明与提交正文(决策 74、77);`scripts/verify-distribution.sh` 在构建时检查,漏进去会构建失败(决策 116)。`.claude/commands/wrapup.md` 的描述是 Claude Code 看到的触发说明,Skill 的描述改了触发词时它也要改。

### 规则 11 · 安装器 Skill 变化 → 获取链路、skills.sh 与适配器对齐

**触发**:`skills/project-consistency-installer/` 或 `.claude/commands/引入一致性机制.md` 变化。
**动作**:
- 保持安装行为只存在于 `skills/project-consistency-installer/SKILL.md`,Claude 命令只做薄适配;
- 验证 `fetch-kit.sh` 不修改目标项目,会拒绝外层校验不符、内部文件篡改、来源元数据异常与不完整 Release;
- 对齐 README 的 skills.sh 命令、`初始化新项目.md` 的机器级安装与绿地排除项;
- 用 skills CLI 验证仓库能发现 `project-consistency-installer`,并校验其 `SKILL.md` 与 `agents/openai.yaml`。

### 规则 12 · 发布边界变化 → 白名单、构建、获取与负向污染测试

**触发**:`distribution/manifest.txt`、`distribution/public-paths.txt`、`scripts/build-distribution.sh`、`scripts/verify-distribution.sh`、`scripts/publish-public.sh`、`.github/workflows/distribution.yml` 变化,或产品文件新增 / 删除 / 改名需要进入干净发布包,或新增顶层文件 / 目录。
**动作**:
- 逐文件更新白名单,不得用“复制整个目录再排除”的黑名单替代;
- 新增顶层文件或目录、`docs/` 文档时判断是否公开:公开的加进 `distribution/public-paths.txt`,内部的不加;公开文件不链接内部文档,不写本机路径与个人信息(决策 78);
- 推送前用 `scripts/publish-public.sh` 生成公开版,核对文件清单与新历史中无个人信息,并在公开版上跑测试与构建;脚本按只放在本机的私人信息词表(内部仓库的 `.git/info/pck-private-words`)检查新增提交的说明与改动,出现新的私人名称时先补进词表(决策 116);触及公开文件的提交,写提交说明时就不要带私人项目名、本机路径;
- 本地构建并验证目录、压缩包、来源元数据、内部逐文件 SHA-256 与外层校验值;
- 负向验证 PROJECT、AGENTS、CLAUDE、套件真实联动目录、真实决策档案、`.DS_Store` 或额外文件任一进入产物都会失败;
- 对齐安装器的 Release 资产名、元数据 schema、缓存完整性检查和 `v*` 标签工作流;
- 对齐 PROJECT、README、初始化指南、机制索引、设计说明与 CHANGELOG。

### 规则 13 · hook 变化 → 跨平台逻辑、双宿主接线与安装器对齐

**触发**:`.agents/hooks/` 下的 hook(每轮提示、压缩后提醒及其 `.ps1` 适配器、自检 `selfcheck.mjs`)、`.agents/skills/wrapup/scripts/hook-trace.mjs`、`.claude/settings.json` 或 `.codex/hooks.json` 变化。
**动作**:
- 保持提醒判断只存在于跨平台 Node 脚本,`.ps1` 只做 Windows 路径定位与 stdin 转发,宿主配置只保存接线(UserPromptSubmit、SessionStart);
- Claude Code 提醒 `/wrapup`,Codex 本地客户端提醒 `$wrapup`;每轮提示同时输出 `systemMessage` 与 `additionalContext`,压缩后提醒给 Agent 的 `additionalContext` 保留,Codex 显式接线另输出简短 `systemMessage`,恢复完成由 Agent 按实际结果反馈;其他宿主不新增用户提示;都不得自动执行 wrapup、同步、commit 或 push;
- 出错一律静默放行;吞掉的错误经 `hook-trace.mjs`(`.ps1` 适配器按同一格式)在 Git 公共目录留一行;自检按新的接线与输出仍能逐项判断通过与否(`scripts/test-hook-observability.mjs`);
- 对齐安装器对 `.claude/settings.json` 无 shell `args` 接线、Codex `commandWindows`、`.codex/hooks.json` 与 `.codex/config.toml` inline hooks 的增量合并和冲突处理;
- 对齐绿地初始化、PROJECT 地图、README、机制索引、设计说明和分发白名单;
- 在 macOS / Linux 与真实 Windows / `windows-latest` 验证每轮相关变化提示、子目录启动、压缩与非压缩事件、Codex 显式反馈和失败留痕;平台未运行的场景单列缺口。Codex hook 信任及宿主实际触发另行确认,静态接线检查不代替它们。

### 规则 14 · 正式版本变化 → Skill、分发元数据与 Release 标签锁步

**触发**:`一致性机制/VERSION`、安装器 `metadata.version`、分发版本字段、CHANGELOG 版本标题或 `v*` 发布规则变化。
**动作**:
- 保证 VERSION、安装器 metadata、`v<VERSION>` 标签和分发元数据一致;
- CHANGELOG 使用 `vX.Y.Z — YYYY-MM-DD` 标题,并按兼容性影响解释 major / minor / patch;
- 包必须含 `kit_version`、`mechanism_revision` 与 VERSION;获取脚本只接受 2.0 及以后的包,按当前文件集合校验,不再验证旧版本的包(决策 135);
- 收尾指针 `refs/pck/synced` 只经共享模块 `synced-ref.mjs` 更新(普通收尾经 `synced-guard.mjs`,并进主线经 `task.mjs land --finish`);installer、初始化与 wrapup 不保留第二套指针操作逻辑;
- 负向验证错误 tag、Skill metadata、包内 VERSION 或分发元数据任一不一致都会失败。
