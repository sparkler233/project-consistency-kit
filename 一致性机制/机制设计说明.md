# 项目一致性机制 · 设计说明

<!-- 一致性机制 version: 2026-10-03 -->

> **本文档受众**:套件维护者、想理解这套机制为什么这样设计的人。2.0 起本文件只留在套件仓库,不再装进用户项目(决策 77);用户项目里机制怎么运行见 `一致性机制/运行规则.md`。
>
> **本文档目的**:说明机制的设计、每个设计选择背后的"为什么",以及取舍时考虑过的边角问题。
>
> **一句话**:本机制让 AI 协作的项目能**跨会话不走样**——新会话能完整接上上次,改动能系统落盘,文件之间的隐性依赖不会慢慢腐烂。

---

## 一、它解决什么问题

任何持续演进的项目,文件之间都会长出大量**隐性联动**:改了 A,B/C/D 理应跟着改,但没人记得。

| 一个改动 | 其他理应跟着改的地方 |
|----------|--------------------|
| 拍板一条重大决策 | 决策记录、相关方案文档、对外口径 |
| 改了某个中枢文档 | 引用它的下游文件、状态清单 |
| 新增/删除一类产物 | 目录的状态描述、地图、索引 |
| 与外部对接 | 沟通记录、可能受影响的计划 |

靠人或 AI 的注意力维护这些联动,**漏改是迟早的事**。漏改的后果不是立刻爆炸,而是慢慢腐烂——某天你以为某个口径定在 A 文件,结果 B、C 还停在两版前。本机制就是专门兜底这件事的。

它还顺带解决另一个问题:**会话不连续**。AI 协作常常一个会话做一半,新会话开局对"上次做到哪了"一无所知。本机制用 git 当"项目记忆",让新会话通过一个可复用工作流装载回完整状态。

## 二、机制总览(2.0)

```
┌─────────────────────────────────────────────────────────┐
│ git 层 —— 事件源与历史                                     │
│  "发生了什么"由 git diff/log 回答;决策全文与过程历史写在     │
│  提交正文(`Decision:` 等 trailer 可检索),不另建日志或档案。 │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────┐
│ 现状层 —— 少量文件记录"现在成立什么"                        │
│  PROJECT.md:入口(目标与边界、总体状态、阅读入口、关键决策);   │
│  「待提交」放刚拍板的决策全文,「最近决策」按 git 生成 10 行。 │
│  一致性机制/文件联动目录.md:改了什么还要查哪里。              │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────┐
│ 规则层 —— 一致性机制/运行规则.md                            │
│  拍板即落盘、不重复记录、提交写明状态变化、二进制、何时用      │
│  catchup / wrapup。机制文件,由安装器管理;AGENTS.md 的      │
│  接入块只放一行引用和压缩后恢复指令。                        │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────┐
│ 工作流层 —— 仓库级 Agent Skills + 脚本                      │
│  catchup(入向):两层读取,恢复项目状态                        │
│  wrapup (出向):检查联动、迁出决策,一次确认后提交并推进 synced │
│  scope / decisions / synced-guard / task 等脚本做机械步骤    │
└─────────────────────────────────────────────────────────┘

  + 宿主适配层:Codex 直接发现 `.agents/skills/`;Claude Code 用 `.claude/commands/` 薄适配器转发。
  + 分发引导层:机器级 `project-consistency-installer` Skill 获取并校验套件,增量引入或升级项目。
  + 制度件(hook):Stop 收尾提醒——工作区有未同步改动时提示运行 wrapup(决策 10);SessionStart 压缩后提醒——提醒重读规则(决策 114)。
  + 并行(实验性,决策 105–115):各会话在自己的 branch + worktree 上工作,task.mjs 做同步与合并,UserPromptSubmit 每轮提示报出相关的主线变化。
```

### wrapup 的流程

```
1. 收集变化:scope.mjs 一次给出基线、基线后的提交与工作区(含未跟踪文件摘要)
2. 回看对话:已拍板但未落盘的内容列入计划补写
3. 拟一份计划:按联动目录检查受影响资料;「待提交」有决策时由 decisions.mjs plan 给出提交正文与「最近决策」变化
4. 一次确认:维护计划、拟提交文件(用文字标明状态)、提交说明全文、synced 条件一起展示
5. 执行:维护 → decisions.mjs apply --commit(写说明、提交并核对)→ guard 推进 synced(仅 canonical;并进主线时由 task.mjs land --finish 推进);分支上不先确认
6. 固定分项报告:完成 / 跳过 / 失败 / 必要但未完成 / 未核对范围 / 提交与 synced / 业务遗留
```

### catchup 的两层

```
第一层 概况:PROJECT.md、运行规则、scope.mjs --overview(基线以来的变化、最近 15 条提交标题、目录一层、并行与推送异常)
第二层 细节:按任务从 PROJECT 阅读入口读对应主题文档,不做全景扫描
```

上下文被压缩后不重跑 catchup,按 AGENTS 接入块里的指令重读 PROJECT 与运行规则(决策 53)。

## 三、关键设计决策与"为什么"

下面逐条解释每个选择——做了什么、为什么这样选、代价是什么。这些理由是机制的精华,换任何项目都成立。

### 决策 1 · 用 git 当事件源

**做了什么**:项目纳入 git;`/wrapup` 用 `git diff` 知道本轮发生了什么。

**为什么**:
- 让 AI 边干边手维护一份"事件日志",依赖纪律,**会忘**(这是实践中反复观察到的弱点)。
- git 自动捕捉所有文件变化,**零纪律**。
- 顺便拿到完整版本控制(diff、回滚、历史追溯)。
- 概念干净:**"事件 = git 看见的文件变化"**。

**代价**:B 类事件(决策、对接——发生在对话里,不直接产生文件改动)git 看不见 → 需要"立刻写进文件"的纪律配合(决策 3)。

### 决策 2 · 联动规则用"中枢文档 + 例外"模型

**做了什么**:联动目录分两部分——
- **Part A 中枢清单**:列 4–10 个"项目关键文档",`/wrapup` 时主动检查每个改动是否影响它们。
- **Part B 例外规则**:只列"AI 容易漏判"或"机械化应固定执行"的少数特殊联动。

**为什么不穷举每种联动**:
- 项目一大,穷举式规则会膨胀失控。
- 加新文件类型时,穷举式必须同步加规则,**忘加 = 漏覆盖**(消极错误,难发现)。
- 中枢文档变化慢、好枚举;例外规则按需补,自然收敛到"刚好够用"。
- 其余靠 AI 临场判断填补。

**代价**:AI 判断可能漏。靠两层兜底——中枢清单保证"最重要的几个文档总会被检查",例外清单显式化"AI 反复漏判的具体规则"。新发现的稳定联动 → 补进 Part B。

### 决策 3 · B 类事件 safety net

**问题**:决策、对外对接、口头约定这些事发生在对话里,本身不产生文件改动,git 看不见 → `/wrapup` 会漏。

**解决**:`/wrapup` 第一步专门干这件事——回看本次对话,找"已发生但还没写进文件的 B 类事件",列清单问用户"要补写吗?",确认后立刻写入目标文件,于是 git 就能看见了。

**canonical 落点钉死**:决策的规范落点 = `PROJECT.md` 的“关键决策记录”(联动目录有对应规则)。**钉死单一落点**,避免“决策有时落项目事实、有时落 Agent 指令、有时两边都没有”的不一致。该落点原在 CLAUDE,后由决策 15 迁移到 PROJECT。

**局限**:safety net 只够得到**当前会话**的对话。跨会话未落盘的 B 类事件捞不回——所以**结束会话前建议跑一次 `/wrapup`**。为堵住「忘跑就结束会话」的静默丢失,已实装 **Stop hook 收尾提醒**(见决策 10):有未同步改动时在回答末尾提示收尾——只提醒不行动,「兜底不门禁」的气质不变。

### 决策 4 · 二进制按"值不值得留版本史 × 体积"分类处理

git 对二进制做不到 diff,且不做 delta 压缩(每版完整存储,一张 5MB 图改 10 版 = 仓库里 50MB)。所以不能无脑全进 git。策略按类:

| 类别 | 例子 | 处理 | 理由 |
|------|------|------|------|
| **文本/矢量** | `.md .txt .json .csv .svg` | 普通 git | 能逐行 diff,天生适合 git |
| **栅格图** | `.png .jpg .jpeg .webp .gif .tif .tiff .bmp .heic` | **Git LFS**(进 git,有版本史) | 值得版本化、数量多、体积中等;LFS = 指针进 git、字节进单独存储,既留版本史又不撑爆仓库 |
| **设计源/PDF/Office/字体/媒体** | `.psd .ai .indd .pdf .docx .ttf .mp4` | `.gitignore` + `_manifest.md` | 单文件可达数百 MB(吃 LFS 额度),或可替换/外来/终端产物 |
| **试稿(任意二进制)** | `_drafts/` 内 | `.gitignore` 整体忽略 | 迭代废版不进 git、不占 LFS 额度——成本控制的主开关 |

> **这是默认值,按项目可改**:纯代码/纯文字项目可能根本没有要版本管理的图片——那就清空或删掉 `.gitattributes` 的 LFS 行,本机制其余部分照常工作。规则见各项目根的 `.gitignore` / `.gitattributes`。
>
> **破例纳入某个被忽略的二进制,必须两步**:先 `git lfs track "<该文件路径>"`(把它纳入 LFS),再 `git add -f`。`git add -f` 只绕过 gitignore,**不会**自动走 LFS——少了前一步,几百 MB 的文件会按完整 blob 进普通 git、每改一版全量再存,正是本决策要防的事故。项目若未启 LFS(如删了 `.gitattributes` 的纯文字项目),先 `git lfs install --local`;只是"想留着"、不需要版本史的二进制,走 manifest 登记即可,不必破例进 git。

**被 gitignore 的二进制目录靠 `_manifest.md` 翻译**:git 看不见这些目录的内容,放一份 `_manifest.md`(纯文本)记录 git/LFS 不管、但又重要的信息——**用途 / 来源 / 授权或版权**(有视觉 / 设计方向的项目可再加「风格基准引用」)。manifest **不记**文件清单/增删/版本(那些归 git/LFS 或 `ls`),只记这几样。**只在含二进制的素材/大文件目录铺**,纯文档目录不要。

### 决策 5 · 草稿双轨(仅二进制适用)

二进制反复迭代会堆积"v1/v2/v3",若都进版本管理会污染、且吃 LFS 额度。约定:试稿放 `_drafts/`(整体 gitignore),定稿后挪出 + 让 git/LFS 接管。

**为什么只对二进制**:Markdown 每次改动本身就是一次清晰的 git 版本,不需要"草稿/定稿"区分;二进制才有"看不见的迭代"问题,需要隔出一个非正式工作区。

### 决策 6 · `/wrapup` 是兜底,不是门禁

用户可以随时手工改文件、手工 `git add` + `commit`。`/wrapup` **不是**"必须跑才能保存",它只是把"漏的联动"系统性补上、把改动收尾。重要节点(多条决策、口径更新)建议跑一下,平时想跑就跑。

### 决策 7 · commit 由用户确认,不自动提交

commit 可能成为推进 sync horizon 的目标,是个单向动作。所以 `/wrapup` 把联动改动写完后,先展示完整提交范围并取得明确确认,再由 AI 起草一句话 message,**问过用户**后 `commit`;feature branch 的 commit 只形成 branch checkpoint,不推进项目级 horizon。

**push 同理由用户负责**:`/wrapup` 只到本地 commit + guard 推进本地 `synced` 为止,**不自动 push**。本机制按**单机**设计——云端 remote 只作备份,何时 push 由用户决定。多机协作要留意一个坑:`synced` 是本地 tag,guard 移动它后远端不会自动跟随,需 `git push --force origin synced` 才能共享 horizon;另一台机器还必须重新确认本地 canonical branch 配置。

### 决策 8 · sync horizon 用 `synced` tag,不用裸 HEAD

"上次同步到哪了"这个边界,**不能**用"最近一次 commit / HEAD"。因为决策 6 允许用户随时手工 commit:一旦用户没跑 `/wrapup` 就自己 commit 了,那笔改动进了 HEAD,下次 `git diff HEAD` 看不到它 → **它的联动被永久跳过,且无任何信号**。

所以 horizon = 独立的 git tag `synced`(canonical branch 上次**已同步**的提交)。canonical 的 `/wrapup` 用它作范围基线,覆盖"已 commit 未同步"+"未 commit"两类;feature branch 改用 `merge-base(HEAD, canonical)` 避免全局 tag 前进后把其他分支变化反向算入。最终由决策 27 的 guard 原子推进 tag,手工 commit 不再隐形。

### 决策 9 · 套件版本治理:统一版本行 + CHANGELOG(由决策 24 扩展)

**做了什么**:每个机制文件(仓库级 Skill 及其 metadata、机器级安装器 Skill 与获取脚本、Claude 命令适配器、本目录三份机制文档、hooks 脚本、分发联动模板)带一行 `一致性机制 version: YYYY-MM-DD` 注释。初版把它称作套件版本:任何机制文件发生真实变化,**全部版本行一起 bump 到当天**,并在套件根 `CHANGELOG.md` 记一行。`project-consistency-installer` 以版本行机械判定目标项目副本新旧;根 `AGENTS.md` 与 `templates/AGENTS.md` 的同步纪律 marker 也随套件统一推进。决策 24 引入正式 SemVer 后,这条日期行保留为**统一文件修订标识**,继续承担混合版本和同日热修检测,不再是对外产品版本。

**为什么**:本机制以"复制"方式分发进 N 个项目。没有文件修订身份,各项目里的副本会静默漂移、且无从判定谁旧——"慢慢腐烂"恰好发生在机制自己身上。"疑似旧版"必须可机械判定(一条 grep),更新提示才不是空话。日期适合回答“这批机制文件是哪天修订的”;对外发布与兼容边界后来交给决策 24 的 SemVer。

**代价**:改机制文件多一道手续(bump 全部修订日期 + 记 CHANGELOG),靠第七节的维护清单兜住。修订标识是套件级、非单文件级——某文件"没改也被 bump"是预期行为,换来机械发现目标项目是否混装不同批次机制件的能力;正式“装的是哪版”由决策 24 的 VERSION 回答。

### 决策 10 · 出向兜底 hook:收尾提醒(纪律 → 制度)

**问题**:决策 3 的 safety net 只能回看**当前会话**的对话,而它是否被执行,完全取决于用户**记得**在会话结束前跑 `/wrapup`。忘了 → 窗口永久关闭,未落盘的 B 类事件**静默丢失**——这是机制中唯一「丢了无信号」的失败模式。

**解决**:初版用一个挂在 Claude Code `Stop` 事件(AI 每轮回答结束)上的纯 shell 脚本 `一致性机制/hooks/收尾提醒.sh`:检测「项目装了机制 + 工作区有未同步改动(`git diff synced` + 未跟踪)+ 本脏周期还没提醒过」→ 给用户弹一行提示「建议收尾跑 /wrapup」。用户在窗口还开着时跑 `/wrapup`,safety net 得以执行,对话里的决策被捞回落盘。决策 23 后续把同一脚本接入 Codex 本地客户端;决策 25 再把判断逻辑迁到跨平台 `.agents/hooks/wrapup-reminder.mjs`,原 `.sh` 降为旧接线兼容包装。

**为什么挂 Stop 不挂 SessionEnd**:SessionEnd 触发时会话已终止,既无法给 AI 喂话、也没有给用户弹消息的通道(查证于 2026-06,Claude Code v2.1.170)。「会话结束时提醒」的正确实现位置,其实是「每轮结束时 + 防唠叨门控」。

**三条红线**:
1. **只提醒,不行动**——不自动跑 /wrapup、不打断 AI(任何分支都 exit 0)、不碰 commit/push,保持「兜底不门禁」(决策 6)的气质。
2. **每个脏周期最多一次**——状态文件(/tmp,按 会话×项目 隔离)防唠叨;工作区清零(跑过 /wrapup)后自动删状态、重新武装。
3. **逻辑与接线分离**——脚本使用常见 shell 与 git 工具完成判断;`.claude/settings.json` 和 `.codex/hooks.json` 只保存宿主接线,不复制业务逻辑。

**覆盖面(诚实)**:hook 读不到对话,**不是** B 类事件探测器,只是「关门前的广播」——保证 safety net 在还能看见对话时被触发。盲区:纯讨论会话(全场零文件改动)+ AI 又恰好违纪未落盘 → 仍会丢。封死盲区需要语义判断(LLM 评估型 hook,每轮判断「有无未落盘决策」),留待将来,暂不做。

**代价**:每轮回答结束多一次毫秒级本地脚本执行;项目级 hooks 首次生效需按宿主完成信任或权限确认。

### 决策 11 · 决策记录轮转归档:工作集留 PROJECT,历史进档案(已废弃,由决策 46–48 取代)

**问题**:“关键决策记录”是项目事实中唯一 append-only 的部分。无上限会让每次 `/catchup` 读取的工作集持续膨胀,但决策 3 钉死的 canonical 落点又不能丢。

**解决**:两层分工——
- **落点随职责迁移**:决策第一时间落 PROJECT 决策记录;操作性内容同时改写进 PROJECT 正文或对应领域文档。记录行只是审计线索。
- **容量上限 + 轮转**:PROJECT 只留最近 10 条;`/wrapup` 发现超限 → 提议把最老条目剪切到 `一致性机制/决策档案.md`,PROJECT 留一行指针。

**关键取舍**:档案不进 Part A、`/catchup` 不默认读取。与 git 同构:PROJECT 决策节 = 当前工作集,档案 = 历史。

**代价**:查很久以前的决策多一跳(打开档案);轮转依赖 /wrapup 跑到——条件触发,超限才有动作,平时零成本。

> 2.0 起废弃:决策全文改由提交正文承载,「最近决策」超限直接删最老行,档案不再维护(见下文决策 46–48)。

### 决策 12 · 安装器双形态:全局命令 + skill(行为正本位置后由决策 19 取代)

**问题**:`/引入一致性机制` 是机器级分发件(偶尔在别的项目里调一次),靠符号链接驻留 `~/.claude/commands/`。但斜杠命令靠**显式记忆**——用户得记得这个名字才用得上;且该目录一旦缺失(换机 / 清理 / 从未落机),安装器静默消失,无信号(2026-07 实测发生)。

**解决**:给安装器加一层 **skill 封装**(`一致性机制/skills/引入一致性机制/SKILL.md`,符号链接驻留 `~/.agents/skills/`):skills 按 description **语义自动触发**(「给这个项目装一致性机制」即可命中,无需记命令名)。SKILL.md 是**纯指针**——只含触发描述与「去读正本」,安装步骤的唯一正本仍是 `.claude/commands/引入一致性机制.md`;两种形态同一文件,**零双份漂移**。

**为什么不进项目**:安装器是套件的分发工具,与全局命令同级、机器级;项目里只需要它的产物(catchup/wrapup 等)。故绿地 rsync 排除它,安装器自身也不拷它。

**代价**:触发层到正本多一跳(skill 先读正本才能干活);机器级符号链接变两处,套件迁移都要重建(登记册已记)。

**后续**:这个方案解决了语义触发,但仍依赖作者机器上的绝对 checkout 路径,且把跨 Harness 安装行为正本放在 Claude 专属命令目录。决策 19 将正本迁到可由 skills.sh 分发的标准英文 Skill,全局命令降为适配器。

### 决策 13 · 套件主页与项目地图模板分离(已由决策 15 扩展)

**问题**：套件根 `README.md` 同时承担 GitHub 项目介绍和新项目地图骨架两个角色。公开展示需要解释机制、安装方式与边界；新项目需要的是带占位符的目录地图。两种内容放在同一文件中，会让项目主页残留模板占位，也会在初始化时把套件介绍复制进目标项目。

**解决**：套件根 `README.md` 只作为公开项目主页，项目地图骨架独立存放在 `templates/README.md`。绿地初始化明确排除根 README，再把模板复制为目标项目的 `README.md`；已有项目缺少 README 时，安装器也只读取该模板。

**为什么**：公开页面和分发模板的受众、生命周期不同。分开后，项目主页可以持续完善而不影响安装产物，模板也能保留必要占位符，不会降低仓库完成度。

**后续**:该决策先把公开主页与模板分开,但仍默认“README = 项目地图”。决策 15 进一步让 README 完全退出运行协议,项目地图迁入 PROJECT,`templates/README.md` 随之取消。

### 决策 14 · 套件项目大脑与新项目 CLAUDE 模板分离(同日被决策 15 取代)

**问题**:套件根 `CLAUDE.md` 原本既是新项目的分发骨架,又是 `/catchup` 必读的当前项目大脑。为了方便复制而保留的占位符,会让套件仓库自己无法记录真实背景、阶段与决策;结果是这套机制在维护自身时反而不能完整 catchup。

**解决**:根 `CLAUDE.md` 只描述套件自身,新项目骨架迁到 `templates/CLAUDE.md`。绿地初始化排除根 CLAUDE 后显式复制模板;增量安装器的新建全骨架和同步纪律注入也统一读取 `templates/CLAUDE.md`,不再把套件自身状态带进目标项目。

**为什么**:项目状态与分发模板的受众、生命周期不同。拆分后,套件可以像任何采用本机制的项目一样维护自己的阶段和决策,模板仍保持可填充、可复制;同时与决策 13 的 README 分层形成一致规则——根文件属于套件,`templates/` 属于新项目。

**后续**:这一步解决了“套件状态不能自描述”,但仍让 CLAUDE 同时承担项目事实与 Agent 指令,且 `/catchup` 会重复读取 harness 已注入的内容。决策 15 把项目事实迁到 PROJECT、指令迁到 AGENTS,CLAUDE 降为链接适配层,因此 `templates/CLAUDE.md` 不再存在。

### 决策 15 · 公开展示、项目事实与 Agent 指令三层分离

**问题**:README 会被 GitHub 默认展示,真实项目往往需要把它写成产品门面、安装/API 文档或用户指南;让它同时承担运行时项目地图会制造职责冲突。另一方面,Codex 会自动加载 AGENTS、Claude Code 会自动加载 CLAUDE,`/catchup` 再完整读取同一内容既重复消耗上下文,也可能让启动时旧版与磁盘新版同时出现。

**解决**:

- `README.md`:对外展示,可选,用户自有;不再是默认中枢或项目地图。
- `PROJECT.md`:项目事实正本,保存背景、流程、地图、阶段与近期决策;由 catchup 显式读取。
- `AGENTS.md`:Agent 工作规则与同步纪律的唯一实体正本;由 Codex 等 harness 自动加载。
- `CLAUDE.md`:Claude Code 适配器;决策 25 后统一只含 `@AGENTS.md`,导入同一规则正本而不复制内容。
- catchup:不再读取 AGENTS / CLAUDE 正文,只验证适配器形态,再读取 PROJECT、Git 与焦点文件。

**为什么**:三个文件分别服务外部读者、项目运行和 Agent harness,生命周期与更新触发都不同。拆开后 README 可自由重写或不存在,Agent 指令不会重复进入上下文,项目事实也不绑定某个厂商文件名。

**代价**:需要迁移旧项目中混在 CLAUDE / AGENTS / README 的内容。初版依赖 Git checkout 保留相对符号链接,只覆盖 macOS/Linux;该平台限制已由决策 25 的通用导入适配器消除。

### 决策 16 · 套件真实联动规则与分发骨架分离

**问题**:`一致性机制/文件联动目录.md` 原本既要描述套件自身的稳定联动,又会被复制到所有目标项目。写入套件专属规则会污染分发骨架;保持通用占位又让套件无法用自己的机制维护自己。

**解决**:根 `一致性机制/文件联动目录.md` 只保存套件真实规则;通用骨架迁到 `templates/一致性机制/文件联动目录.md`。绿地初始化与增量安装器只复制模板,永不复制套件实况。

**代价**:新增一个必须防混用的模板来源;因此套件真实联动目录增加固定规则,要求模板变化时同步检查初始化、安装器、项目地图与公开说明。

### 决策 17 · 出向命令统一为 `/wrapup`(行为正本位置后由决策 18 取代)

**问题**:入向命令已经使用英文 `/catchup`,出向命令仍使用中文名称,分发时形成混合命名;直接改成 `/sync` 又会暗示包含远端 `git push`,与“只做本地联动、commit 和 `synced` horizon”的真实边界不符。

**解决**:出向命令统一为 `/wrapup`,与 `/catchup` 形成“会话开始恢复 / 会话结束收尾”的语义配对。当时文件正本改为 `.claude/commands/wrapup.md`;决策 18 随后把行为正本迁入仓库级 Skill,这里只保留命名结论。“同步纪律”“同步边界”仍作为机制概念保留。

**升级边界**:旧项目可能仍有旧版中文命令文件。安装器必须先比较内容:未定制时经用户确认迁移并移除旧入口;存在项目定制时列出差异并人工合并,不得静默覆盖或让两个出向命令长期并存。

### 决策 18 · catchup / wrapup 以仓库级 Skill 为行为正本

**问题**:`.claude/commands/` 是 Claude Code 专属入口。把完整流程放在那里,Codex 和其他支持 Agent Skills 的 Harness 只能靠自然语言间接读取,且为不同宿主再复制流程会制造多份正本。

**解决**:把完整 catchup / wrapup 流程迁入 `.agents/skills/catchup/` 与 `.agents/skills/wrapup/`。Codex 从仓库根直接发现 Skill,可用 `$catchup` / `$wrapup` 或语义触发;Claude Code 的 `/catchup` / `/wrapup` 文件只负责读取对应 `SKILL.md`,不再保存步骤正文。

**为什么**:行为正本随仓库分发,入口按 Harness 适配。支持 Agent Skills 的宿主直接复用;只支持项目指令的宿主仍可由 AGENTS 引导读取 Skill;Claude Code 保留用户熟悉的斜杠体验。

**代价**:不同 Harness 的显式调用符号并不统一,且 Stop hook 仍需宿主接线。旧项目升级时还必须把命令文件中的定制安全迁入 Skill,不能直接用薄适配器覆盖。

### 决策 19 · 安装器以 skills.sh Skill 分发,按需从 GitHub bootstrap

**问题**:旧安装器 Skill 只是一个指向本机 `~/Developer/项目一致性机制` 的中文名封装。新机器必须先知道仓库地址、手动 clone、再建立符号链接;安装器正本仍在 `.claude/commands/`,与决策 18 的“Skill 正本、宿主薄适配”不一致。

**解决**:把完整安装工作流迁到 `skills/project-consistency-installer/`,采用 skills.sh 可发现的英文小写标识。用户只需从 GitHub 全局安装这个 Skill;运行时优先使用可信本地 checkout,不存在则由随附 `fetch-kit.sh` 把规范仓库获取到机器缓存,验证 remote、干净状态、ref、commit 与必要文件后再开始目标项目迁移。Claude `/引入一致性机制` 降为定位该 Skill 的薄适配器。

**两阶段边界**:skills.sh 只分发机器级引导器,不负责 PROJECT、AGENTS、hooks 等非 Skill 文件。引导器取得整套 GitHub 源后,才把 catchup / wrapup 仓库级 Skill 与其他机制件增量写入目标项目。下载脚本只动机器缓存,项目写入仍由 Agent 展示计划并等待确认。

**安全与版本取舍**:默认 ref 暂为 `main`,每次报告实际 commit;用户可显式指定 tag 或 commit。缓存 remote 不符、有本地改动或文件不完整时立即停止,不强制清理。正式发布稳定后应以套件 release tag 作为推荐 ref,降低可变分支带来的供应链漂移。

**代价**:首次使用依赖 Node.js、skills CLI、Git 和网络;skills.sh 是第三方分发入口,并不替代 GitHub 作为源码正本。离线环境仍需本地 checkout 或预热缓存。

**后续**:决策 22 完成正式发布收敛:安装器不再默认 clone `main`,而是获取带来源元数据和双层校验的干净 GitHub Release;本地源码 checkout 只保留为用户明确提供的开发来源。

### 决策 20 · 自然语言意图作为跨 Harness 的统一用户入口

**问题**:各个 Harness 的显式 Skill 调用方式不同。把 Codex 的 `$project-consistency-installer` 写成默认入口,会让人误以为 Codex 是主要宿主;Claude Code 有自己的斜杠适配器,其他 Harness 也可能使用 Skill 选择器或不同语法。

**解决**:面向用户统一使用“给这个项目引入一致性机制”这句自然语言意图。`project-consistency-installer` 保留为稳定的 Skill 标识,供 Harness 做语义匹配或显式选择。Codex 的 `$project-consistency-installer`、Claude Code 本地开发适配器的 `/引入一致性机制`,以及其他 Harness 的选择入口都属于宿主适配层。

**边界**:自然语言是统一的用户契约,不是新的调用协议。Harness 若不支持隐式 Skill 匹配,用户仍需通过它提供的显式入口选择 `project-consistency-installer`;安装行为始终由同一份 `SKILL.md` 定义。

### 决策 21 · 决策档案实况与分发模板分离(2.0 起档案与其模板均不再分发,见决策 46–48)

**问题**:套件根 `一致性机制/决策档案.md` 起初是空文件,安装器与绿地初始化曾直接把它复制到目标项目。套件自身第一次轮转历史决策后,这条路径会把套件决策 9 一并带进所有新项目,直到端到端安装测试才暴露。

**解决**:套件根档案只保存套件自身历史;新增 `templates/一致性机制/决策档案.md` 作为无项目记录的分发骨架。安装器和绿地初始化只从模板创建新档案,并继续对目标项目已有档案执行整文件跳过,不合并、不覆盖。为修复已安装项目,安装器只把已知泄漏记录的完整原行作为迁移签名:命中后展示上下文,经用户确认才删除精确行,其余项目内容不动。

同日热修可能与旧副本共享 `YYYY-MM-DD` 版本行,所以安装器不能把“版本相同”当成“内容相同”;仍须比较实际内容,区分规范热修与项目定制后再提出更新。

**为什么**:决策档案和联动目录一样包含项目实况,不能因为文件最初为空就把实况文件兼作模板。模板必须在套件产生真实数据后仍保持项目无关。

**代价**:分发链路多维护一个模板来源和一组窄迁移签名;GitHub 获取校验、初始化复制和安装器升级规则必须同时验证模板存在且不含套件决策,同版本更新也多一次内容比较。

### 决策 22 · 源码自举状态与云端分发产物分离

**问题**:源码仓库为了用本机制维护自己,必须在根保留 PROJECT、AGENTS、CLAUDE 链接、真实联动目录和真实决策档案。这些文件作为源码协作状态合理,但 GitHub checkout 同时被安装器当作完整分发源时,源码面与产品发布面混在一起;每新增一种套件实况,都要依赖下游排除规则防泄漏。

**解决**:建立三层边界:

1. `main` 是源码与自举面,完整保留套件自己的运行状态;
2. `distribution/manifest.txt` 逐文件声明可发布产品,`scripts/build-distribution.sh` 只复制白名单并生成来源元数据、内部逐文件 SHA-256、`tar.gz` 与外层校验值;
3. `.github/workflows/distribution.yml` 在普通变更上验证构建,只在 `v*` 标签上用最小 `contents: write` 权限创建 GitHub Release;
4. `fetch-kit.sh` 默认下载 latest 或指定版本的干净 Release,校验外层压缩包、内部文件清单、规范来源和 source commit 后才交给安装器。校验失败不得静默退回源码 clone;
5. 目标项目仍由安装器或绿地初始化从干净源中的 templates 与通用机制件生成自己的 PROJECT、AGENTS、联动规则和决策档案。

**为什么是白名单**:黑名单只能挡住已经知道的套件状态,未来新增文件时默认会泄漏;逐文件白名单让新产品文件必须经过显式评审才能进入发布面。源码仓库因此可以继续 dogfood,而下载产物保持项目无关。

**完整性边界**:GitHub Release 的压缩包 `.sha256` 负责传输完整性,包内 `DISTRIBUTION-MANIFEST.sha256` 负责缓存与逐文件完整性,`DISTRIBUTION-METADATA.txt` 把产物绑定到规范仓库、release ref 和 40 位 source commit。它们提升可审计性,但不替代 GitHub 账号、Release 权限与 HTTPS 本身的信任边界。

**代价**:发布过程新增白名单维护、构建验证和版本标签;机器首次安装依赖 curl、tar 与 SHA-256 工具。源码 main 仍会公开自举文件——干净承诺属于 Release 资产和安装结果,不是源码树的视觉隐藏(2.0 起 GitHub 上的源码改为脚本生成的公开版,见决策 78)。

### 决策 23 · 收尾提醒采用共享脚本 + 宿主接线

**问题**:catchup / wrapup 已通过仓库级 Skill 支持 Codex,收尾提醒却只有 Claude Code 的 `.claude/settings.json` 接线。Codex 用户可以主动运行 `$wrapup`,但忘记收尾时没有同等兜底;为 Codex 再写一份检测脚本又会制造双份逻辑。

**解决**:v1.1.0 让 `一致性机制/hooks/收尾提醒.sh` 作为唯一逻辑正本,从当前会话目录经 git 定位仓库根,并按宿主显示 `/wrapup` 或 `$wrapup`。Claude Code 保留 `.claude/settings.json`;Codex 本地客户端新增 `.codex/hooks.json`,两者都挂 `Stop`。Codex 输出只使用 `systemMessage`,不返回会自动续跑的 `decision: "block"`,因此仍然只提醒、不行动。决策 25 将同一职责迁到跨平台 Node 脚本,没有改变本决策的“单逻辑正本 + 宿主薄接线”。

**为什么用 Stop**:Codex 的 `Stop` 在主 Agent 准备结束当前轮次时运行,能及时显示提醒;`SessionEnd` 要等会话关闭、归档或闲置后才运行,输出也不能继续线程。选择 `Stop` 与现有防唠叨状态机配合,能在对话仍可回看时提醒一次。行为依据 [OpenAI Codex Hooks 文档](https://learn.chatgpt.com/docs/hooks),本机 `codex-cli 0.148.0-alpha.15` 已将 hooks 标为 stable。

**配置与信任边界**:Codex 同一项目层同时存在 `hooks.json` 与 `config.toml` inline hooks 时会合并并警告,所以安装器必须先探测现状:默认创建 `.codex/hooks.json`,已有 JSON 时增量合并,已有 inline TOML 时只合并 TOML,两者并存则交给用户选择收敛方向。项目命令 hook 需要用户审查和信任;安装器只能报告“待信任”,不能把配置写入等同于已经生效。

**范围**:v1.1.0 先覆盖支持项目 hooks 的 Codex 本地客户端与 macOS/Linux bash 路径,不承诺 Codex Cloud;Windows `commandWindows` 当时留待验证。决策 25 已补齐原生 Windows 接线与真机验证。其他 Harness 仍只有在提供等价生命周期 hook 后才增加适配器。

### 决策 24 · 正式版本使用 SemVer,日期降为文件修订标识

**问题**:统一日期版本行能发现复制文件漂移,但 GitHub Release 已使用 `v1.0.0` 标签,分发元数据又只记录 ref 与 commit。用户、安装器和发布页同时看到日期、tag、commit,却没有一个明确的“当前 Kit 是哪一版”;机器级安装器单独由 skills.sh 分发时也无法直观报告它属于哪一版套件。

**解决**:`一致性机制/VERSION` 保存唯一正式 SemVer,整套产品——安装器、catchup、wrapup、hooks、模板与宿主适配器——锁步发版,暂不维护组件独立版本。安装器 `SKILL.md` 的 `metadata.version` 镜像该值,仅用于安装器单独落机后的机器可读身份;构建验证必须保证二者一致。日期版本行继续全套统一推进,语义改为文件修订日期;40 位 source commit 继续提供不可歧义的精确来源。

**发布门禁与 schema 兼容**:分发元数据继续使用 schema 1,以向后兼容字段扩展的方式加入 `kit_version` 与 `mechanism_revision`;v1.0.0 的旧安装器会忽略新增字段并继续接受 v1.1.0 latest,新版安装器则区分 versioned schema 1 与缺少新字段的 legacy schema 1。只有包结构或校验语义发生旧读取器无法安全忽略的破坏变化时才升级 schema。若构建来源是 `v*` tag,tag 必须精确等于 `v<VERSION>`;GitHub Actions 的 tag 发布因此会在版本正本、Skill metadata、tag 或产物元数据任一漂移时失败。legacy 包仍按其历史最低文件集合验证,避免新安装器无法固定或离线使用旧版本。

**目标项目身份**:安装时把 `一致性机制/VERSION` 随机制件写入目标项目。安装器先报告“安装器版本 / 来源 Kit 版本 / 目标现有版本 / 计划动作”,完成后再报告修订日期、ref 与 commit。缺少 VERSION 的旧项目不猜造 SemVer,标为“旧版或未标记”,再用日期行和实际 diff 辅助迁移。

**版本推进**:破坏兼容边界时升 major,新增兼容能力时升 minor,兼容修复时升 patch;仅修改项目自身运行状态、不改变分发产品时不升。日期修订标识仍在任何机制件真实变化时统一推进,同一天的热修通过实际 diff 与 source commit 区分。

### 决策 25 · Windows 使用通用导入、跨平台 hook 与双层验证

**问题**:v1.1.0 的两个关键路径仍依赖 Unix 语义:`CLAUDE.md -> AGENTS.md` 在 Windows 未启用 Developer Mode / 管理员权限时可能被 Git checkout 成普通指针文本;Stop hook 与 Release 获取脚本都直接调用 bash。结果是仓库文件看似存在,Claude Code 却未必加载 AGENTS,原生 PowerShell 环境也无法稳定执行 hook 或安装器。同时 GitHub Actions 仍使用基于 Node 20 的旧 checkout Action,开始产生弃用提醒。

**解决**:

1. `CLAUDE.md` 在所有平台统一为普通文件且只含 `@AGENTS.md`。这是 Claude Code 官方支持的项目内导入,仍由 AGENTS 承担唯一规则正本,并彻底移除 symlink 权限与 checkout 差异;
2. Stop 判断逻辑迁到全 ASCII 固定路径 `.agents/hooks/wrapup-reminder.mjs`,Claude Code 用 exec-form `command + args` 绕开 shell差异,Codex 在 Unix 使用 `command`、Windows 使用 `commandWindows`;旧 `.sh` 只转发到 Node 正本。ASCII 路径避免 PowerShell 5.1 / shell 代码页把中文命令路径静默改写;
3. Windows 安装入口 `fetch-kit.ps1` 只负责定位 Git for Windows 的 Bash、转换路径并调用 `fetch-kit.sh`,不复制下载与校验逻辑;
4. CI 升级到 `actions/checkout@v6`,Linux 与 `windows-latest` 都运行 Stop 状态机测试,Windows 额外构建并经 PowerShell 入口验证干净分发包;
5. 真实 Windows 主机再做一轮 PowerShell 5.1、Git for Windows、Claude Code 与 Codex CLI 联调。CI 保证干净环境可重复,真机暴露实际安装、PATH 与宿主差异;报告必须分别给出脚本 / 适配器直测和宿主端到端结果,不得用前者代替后者。

**为什么不是两份 hook**:PowerShell 与 Bash 各维护一份状态机,会让文件计数、防重复和输出协议逐步漂移。Node 已是 skills.sh 安装链路的既有依赖,用一个无 shell 的跨平台脚本能保住单一行为正本;PowerShell 只留在宿主接线和 Windows 获取入口。

**首轮真机结论与边界**:原生 Windows 需要 Git、Node.js 和 Git for Windows 自带的 Bash(获取脚本复用它);hook 本身只需要 Git + Node。Windows 10 + PowerShell 5.1 真机已通过获取、分发校验、状态机和 `commandWindows` 精确命令直测。当时 Codex 0.148.0 交互界面能识别并显示 Stop hook,却没有提醒输出,因而初步归因为宿主未执行命令;决策 26 的桌面端再验证证明这个归因不准确,宿主已经调度命令,真正失效发生在内联 PowerShell 的二次解析。Codex 项目 hook 仍需用户信任;Codex Cloud 仍不在范围。

**v1.2.1 发布修正**:真实 Windows 的包内验证通过后,`v1.2.0` 标签工作流进一步暴露了源码 checkout 差异:Git for Windows 的 `core.autocrlf=true` 会让 `distribution/manifest.txt` 每条记录带 `\r`,Bash 若直接把整行拼成路径就会误报首个文件缺失。构建与校验脚本因此在白名单读取边界剥离 `\r`;不强制整仓库或目标项目统一换行。已经公开的失败标签不移动,由补丁版本 v1.2.1 承担修复发布。

### 决策 26 · Windows Codex 用 PowerShell 薄适配器隔离宿主解析

**问题**:v1.2.1 的 `commandWindows` 把一段含 `$root` 的 PowerShell 脚本放进双引号,再启动第二个 `powershell.exe -Command`。Codex Windows 会话本身已经由 PowerShell 执行 hook 命令,所以外层会在内层进程启动前就把 `$root` 展开为空;最终 Node 收到错误路径。单独复制 `commandWindows` 直测只有一层解析,因而会假通过;这也是首轮误判为宿主上游缺陷的根因。

**解决**:v1.2.2 新增 `.agents/hooks/wrapup-reminder.ps1`。`commandWindows` 只用不含变量的表达式从 git 根定位这个文件,然后以 `-File` 启动;适配器在文件内完成一次解析,只定位 Node 正本、转发 stdin 并保持失败开放。为避免 Windows PowerShell 5.1 在子进程与外层会话间用本地代码页重新解码 UTF-8,Node 把非 ASCII 字符以 JSON 标准 `\uXXXX` 形式输出;宿主 JSON 解析后仍得到原始中文与 emoji。文件计数、会话防重和输出协议仍只在 `.mjs` 维护,没有形成第二份 Hook 逻辑。

**验证约束**:Windows 自动化不再只直测内层命令,而是从子目录启动一个外层 PowerShell,执行完整 `commandWindows`,通过 `.ps1` 向 Node 传入 Stop JSON,并断言 `$wrapup` 的 `systemMessage`。真机报告仍必须区分“脚本直测”与“Codex 桌面端端到端”;项目与变更后 Hook 命令的用户信任边界不变。

**真机结论**:Windows 10 + Windows PowerShell 5.1 候选包已通过分发反向校验、Node 状态机、外层 Shell 整链路与测试仓库精确命令直测。Codex 0.148.0 桌面端在用户信任变更后的项目 Hook 后,真实 Stop 事件以项目 Hook 通知浮层正确显示“5 个文件”与 `$wrapup`;因此 Windows Codex 桌面端适配在 v1.2.2 候选范围内完成端到端闭环。

### 决策 27 · wrapup guard 保护 canonical horizon,feature 使用 merge-base

**问题**:项目级 `synced` 是所有 worktree 共享的 Git ref。旧 wrapup 在任何 branch 都直接 `git diff synced` 并 `git tag -f synced`:feature 可以错误推进全局 horizon;而 canonical 合并其他工作后移动 tag,又会让旧 feature 的 `git diff synced` 把 canonical 新变化反向算入,检查范围失真。

**解决**:用户确认 canonical branch 后写入当前 clone 的本地 Git config `projectConsistency.canonicalBranch`。wrapup 内部 `.agents/skills/wrapup/scripts/synced-guard.mjs` 成为唯一自动 tag 状态迁移正本:canonical 的 `scope_base = synced`;非 canonical 的 `scope_base = HEAD 与 canonical 的唯一最佳 merge-base`,允许完成本分支联动与 commit,但永远不得推进项目级 `synced`。无共同祖先、多个最佳 merge-base、detached、冲突、`synced` 非 HEAD ancestor 或已有 horizon 时工作区不干净都会 fail closed。

**状态迁移**:installer、首次 wrapup 与日常 wrapup 都委托 guard 创建或推进 tag。初次没有 `synced` 时可把当前 canonical HEAD 建为 baseline,即使工作区已有变化——这些变化仍位于 baseline 之后;已有 tag 的推进必须工作区完全干净。guard 用 `git update-ref --create-reflog` 比较并交换旧 ref,防止并发移动并增加恢复线索;不提供 `--force`。

**克制边界**:这不是 Session 系统。没有 checkpoint command/tag、per-branch horizon、registry、lease 或自动 merge;“branch checkpoint”只是非 canonical wrapup 报告用语。多个 Session 必须用独立 branch + worktree,同一 worktree 并发仍不支持。Stop hook 第一版继续保守读取全局 `synced`,feature 可能收到一次多余提醒;这是 fail-open 的低风险 false positive,观察到真实噪音后再决定是否共享 scope 逻辑。(决策 88、93 起分支上改以任务检查点为基线,见下文「分支感知」。)

### 决策 45–48 · PROJECT 改为入口,决策历史进 git 提交正文

### 决策 49–52、55、58、73、74 · 机制规则独立为运行规则

**问题**:机制规则写在项目 AGENTS 的同步纪律块里,与项目自己的规则混在一起;升级时要在别人的文件里改一段;`@` 导入中文路径文件实测不生效。

### 决策 53、56、57 · catchup 两层读取,压缩后不重跑

**问题**:旧 catchup 全文读取多个中枢、全部未提交文本与全景扫描,一次约 6.5 万 token,大部分与当次任务无关。

**解决**:第一层只读 PROJECT、运行规则与脚本给出的 Git 概况(含最近 15 条提交标题、目录一层清单、并行与推送异常),固定报告“自上次收尾以来”;第二层按任务从阅读入口读细节。实测约 1 万 token。上下文压缩后不重跑 catchup,按 AGENTS 指令重读 PROJECT 与运行规则。

**代价**:catchup 不再主动发现未提交内容与 PROJECT 的矛盾,改由 wrapup 兜底。

### 决策 54、69 · 拍板即落盘,范围扩大到发现与待办

**问题**:决策若等到 wrapup 才写,压缩或会话中断就会丢;对话中顺带发现的问题和待办同样只存在于上下文。

**解决**:拍板时立即写进「待提交」,提交前可改;发现、待办和暂不处理的问题写进所属位置,需要跟进的在 PROJECT 留指针。

### 决策 60、61、66、70 · wrapup 一次确认与固定分项报告

**问题**:维护计划、提交范围、提交说明分多轮确认,用户疲劳;报告格式不固定,“跳过”与“没做成”混在一起。

**解决**:维护计划、拟提交文件、提交说明全文与 synced 条件一次展示、一次确认;文件状态用文字写,不贴 git 代号;报告固定为完成 / 跳过 / 失败 / 必要但未完成 / 未核对范围 / 提交与 synced / 业务遗留,“必要但未完成”不为空不得推进 synced。确认时追加的决策先展示再确认。

### 决策 62、63、64 · 机械步骤交给脚本

**问题**:测试中模型数错「最近决策」行数、抄错基线哈希,改写提示词无法可靠消除;Windows PowerShell 5.1 管道会把提交说明的中文弄坏。

**解决**:`scope.mjs` 一次输出基线、提交、工作区与未跟踪文件摘要;`decisions.mjs` 按位置读取「待提交」,生成提交正文、维护「最近决策」、写提交说明文件并事后核对;提交统一用 `git commit -F <文件>`;决策 104 起每次提交(包括没有决策迁出时)都由 `decisions.mjs apply` 写这个文件。脚本输出 JSON 给模型直接取值,模型写的内容仍是 Markdown;脚本适应模型的写法,不给模型加格式要求。

**代价**:依赖 Node;脚本分工尚未收拢(留到后续版本)。

**脚本负责的结果只由脚本产生**(决策 99):2026-09-27 wrapup 对照实验中,结果正确的运行里仍有模型手工迁出决策再改回重来、为查用法运行 `apply --help` 却被当成一次 apply 执行后手改提交说明文件。这与抄错哈希、数错行数属于同一类:脚本负责的步骤被代做、试探或绕过。处理按类别而不是按现象:所有脚本支持只打印用法的 `--help`,不认识的参数报错且不执行;wrapup 用一段原则(结果只由脚本产生、不代做、不手改脚本生成的内容、用法不清先 `--help`、脚本出错停下报告)代替原来散落的单条禁令。

### 决策 93、95、97、98 · catchup / wrapup 精简与性能底线

**问题**:catchup / wrapup 的大部分句子在 2026-09-21 按行为实验的验收标准一次写成,没有去掉单条规则的对照,其中有重复、依据已撤回或针对已不存在步骤的禁令。

### 决策 72 · 分支上不迁出决策

### 决策 82、102 · 联动命中由脚本按路径列出

**问题**:同一个 wrapup 测试场景跑两次,一次认为对外说明要跟着改、一次认为不用;联动漏查靠改提示词消除不了。

**解决**:`linkage.mjs` 读联动目录中每条规则「触发」行里反引号内像路径的内容(含 `/`,或形如「名字.扩展名」),与本次范围(基线后已提交与工作区改动)的文件比较,相同或位于该目录下即命中;`scope.mjs` 默认模式输出 `linkage.rules_hit` 与没有路径可比的 `rules_not_checked`。脚本只回答「至少要看哪几条规则」,不解析附加条件、不判断规则是否成立、不改文件;要改什么仍由模型读规则原文判断。代码块中的格式示例不算规则;联动目录缺失或认不出规则结构时报 `recognized: false`,不报错。分发模板的「项目联动关系」改为「小标题 + 触发 + 动作」,新装的项目才能用上;已安装的项目不强制转换。

**补充(2026-09-27 机制审查)**:触发同时写了路径和另一个文字条件(如「`data/` 变化,或新增顶层目录」)时,按路径没命中不等于不相关;脚本按「、,;或 以及」切分句,不带路径、去掉泛指的词后仍有文字的分句算文字条件,这样的规则没命中时列入 `rules_not_checked`。对路径的限定语(「`a.md` 中的资格变化」)与路径在同一分句,不算。宁可多列,不漏(原则:假阳性优于危险的假阴性)。

**代价**:条件型规则(如「超过 10 条」)按路径命中会有噪音,写规则时条件不写成反引号路径即可;只有文字的规则仍全靠模型;文字条件靠分句与泛指词表判断,是启发式,会多列少数规则。报告逐条交代命中规则的处理(「🔗 联动」行)与只提示的联动要落盘(决策 89)曾在并行候选中试用,几轮真实会话都没起作用——逐条交代逼不出逐条核对,中端模型还写了不真实的「已核对」——转正前删去(决策 112);联动内容是否真正核对仍靠模型。

### 决策 85、88、93、94 · 分支感知:任务检查点与分支状态

**问题**:catchup 在分支上只知道与主线的分叉点,不知道这个分支是为什么开的、做到了哪里;主线上只能报出「有个未合入的分支」的名字。遗留的实验分支、隔几天回到分支上继续,单人单会话同样会遇到。Stop 提醒在分支上读全局 `synced`,主线前进或刚做完检查点都会误报。

**解决**:分支上的 wrapup 提交就是任务检查点:任务没做完或之后可能换 Session 接手时,说明段写「目标 / 进度 / 还剩」三行(目标写整个任务,还剩写这个任务还有什么没做);`decisions.mjs` 自动加 trailer `Task: <任务名>`(沿用上一个检查点,没有则用分支名)。`scope.mjs --overview` 读出:在分支上给 `current_branch_state`(最近检查点的说明与之后的提交;与主线的分叉点、领先 / 落后、两边改动的文件及交集、试合并结果),在任何位置给 `other_branches`(每个其他分支的任务名、「还剩」、领先 / 落后、能否干净合并)。找检查点先查分支的 reflog,查不到再沿 first-parent:只用 first-parent 会在「主线合并分支后分支快进接回主线」时丢失检查点;reflog 在各 worktree 间共享,新开的分支里也不会有别人的检查点。Stop 提醒在分支上用同样找法,以最近的检查点为基线,没有检查点时用分叉点,检查点已进主线且分支已接回时用较新的分叉点。

**为什么先于并行流程转正**(决策 93):这些都是 Git 事实,价值不依赖多个 Agent 同时工作;可集成标记、集成脚本等并行闭环部分仍在候选目录验证。同时删去 catchup「顶层目录在入口中都未提及时提醒」:入口落后是改动造成的,只读的 catchup 改不了、每次会话重复报,「提到」也难以判定(决策 61 已为误报补过一次)。

**三行为什么不强制**(决策 94):决策 91 曾让脚本查三个标签、缺了不提交,因为读本副本第一轮中两个分支都漏写了说明;但单人用短期分支时每次收尾都要写,负担与收益不相称,改由模型判断。

**代价**:任务状态只来自检查点说明,脚本不检查有没有写、写得对不对,漏写时接手的 Session 只能靠提交标题与改动判断;克隆来的仓库里其他分支没有 reflog,此时退回 first-parent,集成须用 `--no-ff` 才能保住检查点;Git 低于 2.38 时试合并标为 `unavailable`。

### 决策 105–115 · Core 并行:一个人同时驾驶多个会话

**问题**:2.0 之前,并行只有一句「各用独立 branch + worktree」,怎么把主线同步进分支、怎么合回主线、合的时候查什么都没管。第一版设计(决策 105)按「派活」来做:主线上有一个会话负责集成,任务会话做完标记「可集成」,冲突退回任务会话。真正让几个会话同时运行时(Codex `gpt-6-sol` medium),会话恰恰在规则要它停下等用户的地方越界:任务会话自己集成;主线会话替任务会话同步,被禁止后派子代理去做并报成对方的工作;可集成标记未经用户同意就加上。

**定位**(决策 107):Core 并行支持的是用户同时驾驶几个会话、边做边纠正方向,不是派活——派活是宿主子代理的用途。所以主线上不放会话,对哪个会话说「并进主线」,就由它自己同步、检查、合并(决策 108);提示只报事实,要不要同步、打断手上的事由用户决定。

**只守三条**(决策 109):主线只通过检查过的合并前进,不改写主线历史;停下时把现状(目标、进度、还剩)写进分支上的检查点;只写自己的分支和 worktree,不动别人的分支与未提交改动。怎么分工、谁建 worktree、何时同步、何时回到单线程,都交给宿主与用户。三条写在运行规则第四节,平时干活时就在上下文里(决策 113;原写在 wrapup Skill,中端模型平时读不到,手抄了主线改动)。

**解决**:
- `task.mjs` 做全部 Git 操作:`start`、`sync`、`land`、`close`。`land` 把未提交改动先存为检查点、同步主线,引导合并版 wrapup(在分支上迁出决策,记下 `Land-Checked: <主线提交>`),`land --finish` 做合并提交(第一父提交是主线,第二父提交是合并版 wrapup 的提交 C)、快进主线、推进 synced。用 C、M 两个提交而不是一个:快进失败很常见,C 留在分支上,重新同步后再做一个 M 即可;重新同步后,主线新增的改动与本分支不相关就不重新检查(决策 110)。主线只经 `merge --ff-only` 或带旧值的 `update-ref` 前进,别人抢先时 Git 拒绝,不改动任何东西。
- 每轮提示(`parallel-notice.mjs`,`UserPromptSubmit`):只在主线变化与本分支相关(文件交集、主线一侧命中联动规则、试合并冲突)时出现,同时给模型与用户,末尾只说同步用什么命令。宁可多报,不漏。
- 分支上提交不再先确认(决策 111):用户说「并进主线」本身就是授权,摘要也没人逐条看;主线上仍确认一次。
- 「最近决策」按 git 历史整段生成(决策 81、88):两个分支各自迁出决策再合并,索引不会重复或错乱,冲突时由脚本重新生成。
- 压缩后提醒(`compact-reminder.mjs`,`SessionStart` 的 `compact` 来源,决策 114):长会话被压缩后,运行规则可能随 catchup 读入的内容一起被压掉;hook 重新提醒重读,在分支上另附三条。它只把规则交回给模型,不保存状态,与决策 41 不冲突。wrapup 的描述写明「收尾」「并进主线」,宿主一直把描述放在上下文里。

**为什么提前发**(决策 115):决策 92 定的转正条件是「转正前待做」四件都做完;其中用户实际驾驶、联动核对由谁兜底、重复运行都要靠真实使用推进。先以预览版(须用户明确获取)交给真实使用,已知限制写进发版说明。

**验证**:回归测试覆盖开工、同步、冲突、两个会话同时合并、主线目录不干净、收工与各种拦截;Claude Code 桌面版预检(两个 worktree 会话各合并一次,一次有冲突);Codex 小轮 `gpt-6-sol` medium 通过,`gpt-5.6-luna` max 修改后重跑通过(「收尾」、同步、分支上的 PROJECT 状态、冲突后的目录都对了),新出现一次用户拍板的事没被记成决策。

**代价**:每种设置只跑过一次,Windows 只有 CI 回归测试;两个会话先后合并时 PROJECT 总体状态一段几乎必然冲突;联动内容是否真正核对、压缩后是否守规则都还靠模型;脚本拦不住绕开它的手动操作(如自己把分支合进主线);hook 只在项目受信任时运行,Codex 沙箱下合并须把主线目录设为可写;Claude Code 桌面版的 worktree 在仓库内,须写进 `.gitignore`。

### 决策 116 · preview.3 发布前审查的修正

**问题**:preview.3 公开发布前做了一轮整体审查(只查不改),发现一处真缺陷和几处自己的规则没守住的地方。

**解决**:
- **提交必须有标题。** `decisions.mjs apply --commit` 没有 `--title` 时拒绝执行。原先会照样提交:Git 把提交说明的第一段当标题,新分支上说明只有一行 `Task:` 时它成了标题、不再是 trailer,这个检查点之后找不到,而脚本报告的是提交成功——「停下时把现状写进检查点」这一条在没有任何提示的情况下落空。标题末尾的〔决策 N〕改由脚本补上:它是从「待提交」机械得出的,不该靠模型手写。
- **最近提交沿 first-parent。** 并进主线会留下一个合并提交和与它同标题的第二父提交,再加同步提交与合并前检查点;catchup 的最近 15 条里一次合并占两三行,高频合并时这份列表被占满。沿 first-parent 后一次合并只占一行;决策索引另行遍历全部历史,不受影响。
- **分发文件不写套件仓库的决策编号,并由分发校验检查。** 这条规矩(决策 74)原先只靠人记,转正并行时带进去 7 处,其中两处(wrapup Skill、`task.mjs land` 的输出)会被用户项目里的模型读到;用户项目的决策也从 1 编号,模型会当成自己项目的决策。现在构建时检查,漏进去就构建失败。
- **Git 版本不够时明说。** 并行的同步用到 Git 2.35 的冲突格式(冲突块里带原文),试合并用到 2.38;`task.mjs` 开头检查版本,低于 2.38 时拦下并说明,不让后面的命令以看不懂的错误失败。
- **公开版生成后检查私人信息**,见下文「决策 78」。
- 其余是说法更正:Claude Code 读的 `/wrapup` 命令描述也写明「收尾」「并进主线」(决策 114 只改了 Codex 读的 Skill 描述);安装器突出 Codex 的 hook 审查(桌面端可能不弹出审查窗口,没批准时 hook 不运行也不报错);收尾提醒的文字不再用「同步」(它现在指同步主线)。

**没有做的**:把 `task.mjs land --finish` 推进 synced 的逻辑收进 guard。guard 的条件是「在主线上、工作区干净」,而并进主线是在任务分支的 worktree 里完成的;只把「guard 是唯一入口」的说法改成如实描述。

### 决策 118 · 做完一项工作时建议收尾

**问题**:收尾提醒(Stop hook)在有未收尾改动时提醒,第一次出现改动就响,时机更接近开工;而最适合收尾的时刻是「一项工作做完了」,这是 Git 看不出来的事实。按上下文用量提醒收尾的试验则被 Codex 的频繁压缩推翻:用量压缩后回落、重新计数,每轮压缩都会再提示,成了噪音。

**解决**:运行规则第三节加一条规则:一项工作做完(改动已验证、没有紧接着的下一步)时,模型主动向用户建议收尾;进行中不打断,是不是到了段落由模型按当前任务的具体情况判断。主线上收尾要先经用户确认,所以只建议、等用户决定;任务分支上收尾只是写检查点,可以直接做、事后报告。这一句规则两个宿主通用,不依赖宿主的内部记录格式,不新增 hook。

**试用与转正**:先写在套件源仓库自己的 `AGENTS.md` 里试用。试用中模型在一项排查进行时没有打断、告一段落后才提出收尾,符合要求,用户判断有效后移入运行规则(分发文件,走发版纪律),并删掉 `AGENTS.md` 里的试用条。

**没有做的**:按上下文用量的提示(Claude Code 窗口大、压缩少,压缩前提醒一次仍有用)仍是仓库内的试用,不分发;Codex 不接线。用户那一侧是否看到该提示、从头接线的会话里的效果,仍待观察。

### 决策 127、129、131 · 启动与保存节奏的产品职责

**演进**：用户明确启动只需理解项目整体和工作现场，反馈应简明易懂，让人看得出 Agent 已经接上项目。catchup 因此移除任务调查步骤和逐条状态汇报，保留现场事实、交接信息、重要异常和特有的 Git 历史查阅约定。没有任务时不自选任务；已有任务时恢复后继续开展。

**引导**：按需用容易理解的产品概念说明并行收益和下一步。Git 准备由 Agent 在获准后完成，用户只承担宿主必须手动完成的动作；不新增模式状态或通用会话编排。独立试用发现仅说“技术操作由 Agent 处理”仍可能把工作目录准备交给用户，因此明确了这处分工。

**保存**：决策 118、120 的固定完成提醒调整为结合对话积累和进度的自然建议，用户掌握节奏；分支停下时的交接检查点仍保留。收到提醒本身不自动授权提交。

**边界**：这批只调整 Skill、运行规则与配套说明。Stop hook 仍按改动提醒，其触发策略后续另议；启动自检和脚本异常后的接手也未放开。内部候选先做少量隔离试用，不能视为已完成性能底线或长期可靠性验证。

### 决策 129 · 启动的最低限度检查

在已有失败留痕之外，启动检查必要文件能否读取、当前宿主项目级 hook 接线的明显问题。概览通过可选宿主参数调用只读模块，既有完整自检仍用于进一步诊断。未知宿主不凭配置文件猜测，自定义命令与 TOML 内联接线不以不完整解析冒充校验；没有已知错误也不代表宿主已经信任或执行。

正常不逐项汇报；模块只提供具体异常与未检查范围，Agent 解释对当前工作的影响。检查不执行配置中的命令、不修复、不写通过标记；已有失败日志仍保留。这减少了反复运行完整自检的成本，但无法覆盖主程序尚未启动、用户级接线或宿主运行环境等所有失败，缺口应如实说明。

### 决策 121 · hook 可观测性:自检与失败留痕

**问题**:hook 是提醒,不是关卡,出错一律静默放行,不挡宿主。代价是坏掉的 hook 和「没什么可提醒」看起来一模一样。preview.3 发布时 Windows CI 由此逼出四个静默问题(PowerShell 转发的输入带 BOM、非 ASCII 输出被 PowerShell 5.1 解乱、测试脚本的中文注释在 GBK 下吞掉换行、适配器取仓库根目录时静默退出),其中适配器那个自 v1.2.x 就在,一直没人发现。

**解决**:不改静默放行,只加可见性,都靠脚本,不给模型加规则。
- **自检命令** `selfcheck.mjs`:读项目实际的接线(Claude Code 的 settings、Codex 的 hooks.json 或 config.toml 内联写法),在临时仓库里按接线原样运行每个 hook,看退出码、有无输出、输出是否为带预期字段的合法 JSON。临时仓库复制项目自己的 `.agents/` 与接线文件,造出三个 hook 都该出声的场景(任务分支上有未收尾的改动、主线新增了改同一文件的提交、`source=compact`),所以「没有输出」就是坏了。只跑当前平台的接线:Windows 上 Codex 走 `commandWindows` 与适配器,这正是之前静默坏掉的那一段。安装器接线后运行,用户觉得提醒没了时也运行;CI 对本仓库接线也跑一次。
- **失败留痕**:hook 自己吞掉错误(外层异常、输入非空却解析不出、状态文件写不了),或 Windows 适配器找到仓库却跑不起 hook 时,在 Git 公共目录追加一行。放公共目录而不是各 worktree 的 git 目录:并行时换个 worktree 开会话也要看得到别处的失败。输入解析失败只记长度与开头几个字符的码位(足以认出 BOM 一类问题),不记内容——每轮提示的输入含用户的提问。
- **何时不再报告**:自检全部通过时追加 `selfcheck ok`,`scope.mjs --overview` 只给这之后的失败,catchup 有内容时用一行提到。按时间窗口(如 7 天)报告会在修好之后还反复出现;用自检通过作分界,用户修好并确认后自然清零。

**没有做的**:自检不诊断真实项目为什么某次没提示(如没配主线分支、不在任务分支,hook 本就该静默),那要把每个 hook 的判断条件再写一遍,容易误报;宿主是否信任 hook、宿主自己的 PATH 里有没有 node,自检也测不到。

**代价**:模块根本没跑起来(导入的文件缺失、语法错误)或适配器连 Git 都找不到时无处可写,只能靠自检发现。三个 hook 读输入的代码合进 `hook-trace.mjs` 后,收尾提醒也依赖 wrapup 的脚本目录,与另两个 hook 相同;少了这个文件 hook 以非 0 退出,宿主会显示 hook 出错,自检也会报出。

### 决策 78 · GitHub 只放脚本生成的公开版

**问题**:2.0 的设计过程(Core 升级设计、候选快照、各设计稿)与上千个实验证据文件都进了本仓库 git 历史,其中有维护者本机路径、局域网机器用户名等个人信息,此前也从未公开。直接推送整个仓库会把它们连同历史一起公开;新提交删除它们挡不住历史,而一次性改写历史剔除它们,内部文档又会失去 catchup / wrapup 所依赖的 git 跟踪。

**解决**:本仓库作内部工作仓库,保留全部内容与历史,本身不推送。`distribution/public-paths.txt` 列出公开路径(产品文件、README、CHANGELOG、初始化指南、使用示例、本文件与机制 README、AGENTS、CLAUDE),`scripts/publish-public.sh` 从本仓库历史只保留这些路径,接在最初的公开 main(`84d5466`,写成脚本常量)之后生成公开历史,作者统一为公开身份,只改内部文件的提交自动略去。每次都从同一个基整段重新生成,同样输入给出同样的提交号,已公开的提交原样重现,新提交接在后面,可以普通快进推送;生成后检查公开 main 原样包含在新历史里、新提交不重复已公开的提交,否则报错(preview.2 发布时发现:以当时的公开 main 为基会把全部内部提交再重放一遍,而推送照样被当作快进接受);Release tag 打在公开历史上,CI 在公开仓库里构建。

**提交说明也会公开**(决策 116):触及公开文件的提交,它的说明(含迁入的决策全文)原样进公开历史,白名单管不到这里。所以生成后另按一份只放在本机、不进仓库的私人信息词表(私人项目名、本机用户名、邮箱等)检查新增提交的说明与改动,出现词表中的词、或没有词表时报错,不打印推送命令。词表本身含私人信息,所以放在内部仓库的 `.git/info/` 下。

**为什么是白名单**:与分发清单同理,新增文件默认不公开,必须显式加入。公开范围比分发包宽(还含测试、CI、本仓库自身规则),两份清单分开维护。

**代价**:公开版的 AGENTS 与联动目录仍提到不公开的 PROJECT 等文件,只作套件开发规则参考;公开文件不能链接内部文档;推送前要多一步生成与核对。

## 四、文件类型与 git 兼容度速查

| 类型 | 例子 | git diff | 处理 |
|------|------|---------|------|
| 文本 | .md .txt .json .yaml .csv .html .css .js | 🟢 完美 | 普通 git |
| 矢量 | .svg | 🟢 是 XML | 普通 git |
| 栅格图 | .png .jpg .webp .heic | 🔴 二进制 | Git LFS(默认) |
| 设计源 | .psd .ai .indd | 🔴 + 通常很大 | gitignore + manifest |
| Office/PDF | .docx .xlsx .pdf | 🔴 二进制 | gitignore + .md 摘要 |
| 字体/媒体 | .ttf .mp4 .mp3 | 🔴 二进制 | gitignore + manifest |

**核心原则**:所有"决策、文字、规范、记录"都用 .md;需要版本史的栅格图走 LFS;其余二进制当"附件",由 manifest 翻译。

## 五、项目套用本机制后的结构

一个采用了本机制(2.0)的项目,大致长这样(`<...>` 是项目自己的内容):

```
<某项目>/
├── .git/                     版本控制本体(事件源;决策全文与过程历史在提交正文)
├── .gitignore                二进制排除规则(可按项目改)
├── .gitattributes            选择性 LFS 规则(可按项目改/删)
├── README.md                 对外说明(可选,不属于核心协议)
├── PROJECT.md                项目入口:目标与边界、总体状态、阅读入口、关键决策 ⭐
├── AGENTS.md                 项目自己的 Agent 规则 + 接入块(引用运行规则)⭐
├── CLAUDE.md                 只含 @AGENTS.md 的 Claude Code 导入适配
├── .agents/skills/           跨 Harness 工作流正本 ⭐
│   ├── catchup/              SKILL.md、agents/openai.yaml
│   └── wrapup/
│       ├── SKILL.md、agents/openai.yaml
│       ├── references/document-maintenance.md   整理细则(明确要求整理时读)
│       └── scripts/
│           ├── scope.mjs            Git 范围与未跟踪文件摘要
│           ├── decisions.mjs        决策迁出、「最近决策」生成与核对
│           ├── linkage.mjs          联动规则按路径命中
│           ├── task.mjs             并行的开工、同步、并进主线与收工
│           ├── checkpoints.mjs      任务检查点的共享找法
│           └── synced-guard.mjs     canonical / feature 范围与 synced 状态迁移正本
├── .agents/hooks/
│   ├── parallel-notice.mjs    并行时的每轮提示(决策 108)
│   ├── compact-reminder.mjs   上下文压缩后的提醒(决策 114)
│   └── run-hook.ps1           Windows Codex 通用薄适配器
├── .claude/
│   ├── settings.json         hook 接线
│   └── commands/             catchup.md、wrapup.md 薄适配器
├── .codex/hooks.json         Codex 本地 hook 接线
├── 一致性机制/
│   ├── 运行规则.md             机制怎么运行(机制文件,安装器管理)⭐
│   ├── 文件联动目录.md         本项目的联动规则(归项目所有)⭐
│   ├── VERSION                当前完整安装的套件版本
│   └── LICENSE.project-consistency-kit  套件许可副本
└── <项目自己的目录>            正文/代码/素材/产物……
```

> 本文件、机制 README 与 CHANGELOG 只在套件仓库(决策 77)。哪些是机制文件,以运行规则第四节为准。

## 六、给接手 AI 的建议

接手一个用了本机制的项目:

1. 确认宿主已自动加载 **`AGENTS.md`**(或经 **`CLAUDE.md`** 导入的同一内容),不要再显式读一遍;
2. 执行 **catchup**(Codex: `$catchup`;Claude Code: `/catchup`)——读 `PROJECT.md`、`一致性机制/运行规则.md` 与脚本给出的 Git 概况;
3. 按任务从 PROJECT 阅读入口读细节;需要联动时读 `一致性机制/文件联动目录.md`;
4. 上下文被压缩后不重跑 catchup,按 AGENTS 接入块里的指令重读 PROJECT 与运行规则。

若对机制设计有疑问或觉得有更好方案,**先和用户讨论,别直接动架构**——每个看似奇怪的选择背后都有具体权衡,本文第三节解释了这些"为什么"。

## 七、本机制自身的维护

- **改任何机制文件(仓库级工作流 Skill / 机器级安装器 Skill与跨平台获取入口 / Claude 命令适配器 / Codex hook 适配器 / 本目录三份机制文档 / hooks 脚本 / 分发模板)= 一次套件发版**:先按兼容性判断 `一致性机制/VERSION` 的 major / minor / patch,同步安装器 metadata,再把全部 `一致性机制 version:` 行以及根 `AGENTS.md`、`templates/AGENTS.md` 接入块(`一致性机制:接入`)的修订日期推进到当天 + 套件根 `CHANGELOG.md` 记入对应版本(决策 9/24)。
- 机制发生**真实变化**时(不只规则微调),更新本文件。
- 某个决策被推翻时,**保留原描述 + 标注"已废弃"**,不要直接删——留演进路径给接手者看。
- 改本机制的文件也走 wrapup:它会按套件真实 `文件联动目录.md` 检查 PROJECT、AGENTS、公开 README、模板、初始化、安装器与 CHANGELOG,再经确认 commit、推进 `synced`。
- 涉及分发的改动先在本仓库以不进入分发清单的方式试用(候选目录),验证后再转正发版(决策 51)。

## Stop hook 退役(决策 131)

原 Stop 提醒依据 Git 未保存改动,不能证明用户已经结束工作或必须保存。用户认为收益有限,决定在 preview.4 移除逻辑、接线和两个旧包装;此前保留兼容包装的决定相应调整。保存由用户决定,Agent 保留情境建议,并行检查点要求不变。自检与分发只要求每轮提示和压缩后提醒。升级先更新安装器,只清理机制自己的旧 Stop handler 和标准脚本,保留用户自定义 hook。以上历史章节保留原方案的演进依据。

## Codex 压缩反馈(决策 130)

压缩后恢复对用户原本不可见。现在 Codex 接线显式传入宿主参数,hook 向用户简短说明将重读项目说明和规则,Agent 的上下文仍保留实际重读指令,并要求重读后按事实简短反馈。两阶段区分正在恢复与恢复结果,不以 hook 触发保证信息无损。Claude 等其他接线保持原样,不新增用户确认或完整 catchup;Windows 通用适配器仅转发参数。

## 异常恢复的最小范围(决策 132)

脚本未能运行时先尝试恢复;检查发现风险时先解决问题;中途失败先核对已发生的文件和 Git 变化,不盲目重跑。暂时修不好也可以在原授权内记录信息与成果,但仍保留待提交决策,不手改生成内容或接管提交、合并、基线推进。这提供有限兜底,避免模型临场重建 Git 保护逻辑;报告须区分文件落盘和提交成功,完整手工接手后置。

## 收尾指针改为机制专用引用(决策 133)

保留独立指针来定位上次收尾位置,不把它当作项目正确或可发布的证明。当前以 refs/pck/synced 存放,没有时读取旧 refs/tags/synced;新旧提交不同则阻止推进。普通收尾与并行合并共用 synced-ref.mjs,Git 事务同时比较新旧引用和主线位置,更新新指针并删除本地旧标签。migrate 仅保留原位置搬移,不推进检查边界;同仓库 worktree 共享,旧机制须一起升级。普通 push --tags 不带新指针,显式 refspec 或镜像推送仍可能带走。旧章节中的标签方案保留为历史依据。

## 决策的颗粒度(决策 134)

拍板即落盘(决策 54、69)只规定了写入时机,没有规定什么算一条决策,模型容易把每次澄清都当成一次拍板:preview.4 一轮产品讨论记了 36 条,事后合并为 8 条。按这个密度,长程任务会膨胀到难以检索;合得过粗又会让标题塞不下,检索和后续调整都不好指。

现在「待提交」当作可改写的草稿:随时写,同一话题改写原条,收尾迁出前再合并或拆开定稿,保留及时落盘对压缩的保护。颗粒度只给范围和反向限制:一条对应一个话题上定下的方向或取舍,判断标准是新会话不知道它时会不会做反;澄清、补充修正、自然推出的做法与流程进展不另起一条,不相干的话题不并成一条。不设硬性条数上限,也不让脚本提示,具体由 Agent 判断。

## 2.0.0 稳定接口与去掉旧版本兼容(决策 135)

稳定承诺分三档:用户依赖的文件职责、PROJECT 中脚本读取的两个小节、决策历史与 trailer、联动目录格式、日常入口与关键行为、`refs/pck/synced` 与主线配置、两项 hook 接线、获取脚本参数与 hook 自检、版本身份属于稳定;并行等列入实验性;内部脚本的选项与 JSON、措辞与文案属于不承诺。内部 JSON 可以直接调用,但对外承诺稳定会让每次改脚本都背上兼容包袱。

旧版本只有用户自己在用,2.0 是大版本,于是旧版本兼容整体去掉:运行时不再读旧 synced 标签,获取脚本不再按各旧版本的文件要求校验历史包,安装器不再处理 v1.3.0 与各预览版的升级。旧项目由用户让模型手工迁移;原升级细则与 Stop 退役步骤移到不分发的手工升级参考。代价是旧项目升级没有安装器兜底,迁移质量取决于执行的模型和用户核对。项目数据层面的兼容保留:「最近决策」中 git 里没有全文的旧行与 `Decision-Archive` 照常处理。以上 synced 标签迁移、Stop 退役等章节保留为演进依据。

## 改名后的来源仓库标识(决策 136、138)

对外名称改为 Recensio、仓库改名为 `recensio` 时(决策 136),装进项目与机器的标识(`一致性机制/` 目录、接入标记、`refs/pck/synced`、安装器 Skill 名、包名、缓存目录)不随改名变动,只改展示名与地址。分发包元数据的 `source_repository` 是获取脚本校验的来源身份:2.0.1 起改写新地址,获取脚本新旧地址都认,以便继续取 2.0.0 与已缓存的旧包(决策 138)。代价是已装的 2.0.0 获取脚本只认旧地址、会拒收新包,用户须先更新安装器;否掉的做法是 2.x 内包里仍写旧地址、只当身份标识,到 3.0 再切。

英文适配曾定为覆盖公开页面与装进项目的内容(决策 137),评估「安装时选语言、中英两版」后,因一次性改动与说明文字长期双份维护的代价偏大,改为装进项目的内容保持中文、公开 README 以中文为主页、另附英文版(决策 139,取代决策 137)。
