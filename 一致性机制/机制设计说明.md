# 项目一致性机制 · 设计说明

<!-- 一致性机制 version: 2026-08-20 -->

> **本文档受众**:接手某个用了本机制的项目的 AI 协作者,或想理解这套自我维护机制的人。
>
> **本文档目的**:说明机制的设计、每个设计选择背后的"为什么",以及取舍时考虑过的边角问题。
>
> **一句话**:本机制让 AI 协作的项目能**跨会话不走样**——新会话能完整接上上次,改动能系统落盘,文件之间的隐性依赖不会慢慢腐烂。

---

## 一、它解决什么问题

任何持续演进的项目,文件之间都会长出大量**隐性联动**:改了 A,B/C/D 理应跟着改,但没人记得。

| 一个改动 | 其他理应跟着改的地方 |
|----------|--------------------|
| 拍板一条重大决策 | 决策记录、相关方案文档、对外口径 |
| 改了某个中枢文档 | 引用它的下游文件、状态清单 |
| 新增/删除一类产物 | 目录的状态描述、地图、索引 |
| 与外部对接 | 沟通记录、可能受影响的计划 |

靠人或 AI 的注意力维护这些联动,**漏改是迟早的事**。漏改的后果不是立刻爆炸,而是慢慢腐烂——某天你以为某个口径定在 A 文件,结果 B、C 还停在两版前。本机制就是专门兜底这件事的。

它还顺带解决另一个问题:**会话不连续**。AI 协作常常一个会话做一半,新会话开局对"上次做到哪了"一无所知。本机制用 git 当"项目记忆",让新会话通过一个可复用工作流装载回完整状态。

## 二、机制总览(三层 + 一条纪律 + 一个制度件)

```
┌─────────────────────────────────────────────────────────┐
│ git 层 —— 事件源                                          │
│  项目本身是 git repo。"发生了什么"由 git diff/log 回答,    │
│  零纪律、自动捕捉、附带完整版本史。                          │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────┐
│ 联动规则层 —— 一致性的"图纸"                               │
│  一致性机制/文件联动目录.md                                │
│  "中枢文档 + 例外规则" 双层模型:                           │
│  规定"某文件变了,还要回头检查/改哪些其他文件"。              │
└──────────────────┬──────────────────────────────────────┘
                   ▼
┌─────────────────────────────────────────────────────────┐
│ 工作流层 —— 仓库级 Agent Skills                            │
│  catchup(入向):新会话把项目状态完整装载回来                │
│  wrapup (出向):按联动规则把改动落盘、提交、推进 synced      │
└─────────────────────────────────────────────────────────┘

  + 宿主适配层:
    Codex 直接发现 `.agents/skills/`;
    Claude Code 用 `.claude/commands/` 薄适配器转发到同一 Skill。

  + 分发引导层:
    skills.sh 分发机器级 `project-consistency-installer` Skill;
    本地没有套件时,安装器先从 GitHub 获取并验证只读源,
    再把仓库级工作流与机制文件增量引入目标项目。

  + 一条纪律(写在 AGENTS.md,由 CLAUDE.md 导入适配):B 类事件落地
    决策、对外对接、口头约定这些"发生在对话里、git 看不见"的事,
    AI 必须立刻写进目标文件 —— 把"对话里的事"变成"git 能看见的改动"。

  + 一个制度件(hook):Stop 收尾提醒
    工作区有未同步改动时,在 AI 回答结束处提示用户跑 /wrapup
    —— 把"记得收尾"从纪律变成制度(决策 10)。
```

### wrapup 的步骤(0 前置检查 + 5 步主流程)

```
0. 前置检查:不是 git repo / 联动目录不存在 → 退出
1. 自查 B 类事件(safety net):回看对话,找没落到文件的决策/对接 → 提示补写
2. 确定范围:git diff synced(自上次已同步的提交以来的全部改动)
3. 查联动目录:对每个改动,比对 Part A 中枢清单 + Part B 例外规则,推断联动
4. 拟订计划 → 用户确认 → 逐项执行
5. git add → 用户确认 commit message → commit → git tag -f synced(推进 horizon)
```

### catchup 的四层

```
第一层 项目事实:harness 已注入 AGENTS/CLAUDE,只读 PROJECT.md
第二层 项目状态:git log / git status / git diff synced —— 上次做到哪了
第三层 当前焦点:读 git status 里未提交/未跟踪的文件 —— 上次没收尾的活就在那里
第四层 全景扫描:自动派生顶层目录清单并 ls —— 建立对项目实际形态的认知
```

## 三、关键设计决策与"为什么"

下面逐条解释每个选择——做了什么、为什么这样选、代价是什么。这些理由是机制的精华,换任何项目都成立。

### 决策 1 · 用 git 当事件源

**做了什么**:项目纳入 git;`/wrapup` 用 `git diff` 知道本轮发生了什么。

**为什么**:
- 让 AI 边干边手维护一份"事件日志",依赖纪律,**会忘**(这是实践中反复观察到的弱点)。
- git 自动捕捉所有文件变化,**零纪律**。
- 顺便拿到完整版本控制(diff、回滚、历史追溯)。
- 概念干净:**"事件 = git 看见的文件变化"**。

**代价**:B 类事件(决策、对接——发生在对话里,不直接产生文件改动)git 看不见 → 需要"立刻写进文件"的纪律配合(决策 3)。

### 决策 2 · 联动规则用"中枢文档 + 例外"模型

**做了什么**:联动目录分两部分——
- **Part A 中枢清单**:列 4–10 个"项目关键文档",`/wrapup` 时主动检查每个改动是否影响它们。
- **Part B 例外规则**:只列"AI 容易漏判"或"机械化应固定执行"的少数特殊联动。

**为什么不穷举每种联动**:
- 项目一大,穷举式规则会膨胀失控。
- 加新文件类型时,穷举式必须同步加规则,**忘加 = 漏覆盖**(消极错误,难发现)。
- 中枢文档变化慢、好枚举;例外规则按需补,自然收敛到"刚好够用"。
- 其余靠 AI 临场判断填补。

**代价**:AI 判断可能漏。靠两层兜底——中枢清单保证"最重要的几个文档总会被检查",例外清单显式化"AI 反复漏判的具体规则"。新发现的稳定联动 → 补进 Part B。

### 决策 3 · B 类事件 safety net

**问题**:决策、对外对接、口头约定这些事发生在对话里,本身不产生文件改动,git 看不见 → `/wrapup` 会漏。

**解决**:`/wrapup` 第一步专门干这件事——回看本次对话,找"已发生但还没写进文件的 B 类事件",列清单问用户"要补写吗?",确认后立刻写入目标文件,于是 git 就能看见了。

**canonical 落点钉死**:决策的规范落点 = `PROJECT.md` 的“关键决策记录”(联动目录有对应规则)。**钉死单一落点**,避免“决策有时落项目事实、有时落 Agent 指令、有时两边都没有”的不一致。该落点原在 CLAUDE,后由决策 15 迁移到 PROJECT。

**局限**:safety net 只够得到**当前会话**的对话。跨会话未落盘的 B 类事件捞不回——所以**结束会话前建议跑一次 `/wrapup`**。为堵住「忘跑就结束会话」的静默丢失,已实装 **Stop hook 收尾提醒**(见决策 10):有未同步改动时在回答末尾提示收尾——只提醒不行动,「兜底不门禁」的气质不变。

### 决策 4 · 二进制按"值不值得留版本史 × 体积"分类处理

git 对二进制做不到 diff,且不做 delta 压缩(每版完整存储,一张 5MB 图改 10 版 = 仓库里 50MB)。所以不能无脑全进 git。策略按类:

| 类别 | 例子 | 处理 | 理由 |
|------|------|------|------|
| **文本/矢量** | `.md .txt .json .csv .svg` | 普通 git | 能逐行 diff,天生适合 git |
| **栅格图** | `.png .jpg .jpeg .webp .gif .tif .tiff .bmp .heic` | **Git LFS**(进 git,有版本史) | 值得版本化、数量多、体积中等;LFS = 指针进 git、字节进单独存储,既留版本史又不撑爆仓库 |
| **设计源/PDF/Office/字体/媒体** | `.psd .ai .indd .pdf .docx .ttf .mp4` | `.gitignore` + `_manifest.md` | 单文件可达数百 MB(吃 LFS 额度),或可替换/外来/终端产物 |
| **试稿(任意二进制)** | `_drafts/` 内 | `.gitignore` 整体忽略 | 迭代废版不进 git、不占 LFS 额度——成本控制的主开关 |

> **这是默认值,按项目可改**:纯代码/纯文字项目可能根本没有要版本管理的图片——那就清空或删掉 `.gitattributes` 的 LFS 行,本机制其余部分照常工作。规则见各项目根的 `.gitignore` / `.gitattributes`。
>
> **破例纳入某个被忽略的二进制,必须两步**:先 `git lfs track "<该文件路径>"`(把它纳入 LFS),再 `git add -f`。`git add -f` 只绕过 gitignore,**不会**自动走 LFS——少了前一步,几百 MB 的文件会按完整 blob 进普通 git、每改一版全量再存,正是本决策要防的事故。项目若未启 LFS(如删了 `.gitattributes` 的纯文字项目),先 `git lfs install --local`;只是"想留着"、不需要版本史的二进制,走 manifest 登记即可,不必破例进 git。

**被 gitignore 的二进制目录靠 `_manifest.md` 翻译**:git 看不见这些目录的内容,放一份 `_manifest.md`(纯文本)记录 git/LFS 不管、但又重要的信息——**用途 / 来源 / 授权或版权**(有视觉 / 设计方向的项目可再加「风格基准引用」)。manifest **不记**文件清单/增删/版本(那些归 git/LFS 或 `ls`),只记这几样。**只在含二进制的素材/大文件目录铺**,纯文档目录不要。

### 决策 5 · 草稿双轨(仅二进制适用)

二进制反复迭代会堆积"v1/v2/v3",若都进版本管理会污染、且吃 LFS 额度。约定:试稿放 `_drafts/`(整体 gitignore),定稿后挪出 + 让 git/LFS 接管。

**为什么只对二进制**:Markdown 每次改动本身就是一次清晰的 git 版本,不需要"草稿/定稿"区分;二进制才有"看不见的迭代"问题,需要隔出一个非正式工作区。

### 决策 6 · `/wrapup` 是兜底,不是门禁

用户可以随时手工改文件、手工 `git add` + `commit`。`/wrapup` **不是**"必须跑才能保存",它只是把"漏的联动"系统性补上、把改动收尾。重要节点(多条决策、口径更新)建议跑一下,平时想跑就跑。

### 决策 7 · commit 由用户确认,不自动提交

commit 会推进 sync horizon(下次 `/wrapup` 视之前为"已处理"),是个单向动作。所以 `/wrapup` 把联动改动写完后,AI 起草一句话 message,**问过用户**再 `commit`。

**push 同理由用户负责**:`/wrapup` 只到本地 commit + 推进本地 `synced` 为止,**不自动 push**。本机制按**单机**设计——云端 remote 只作备份,何时 push 由用户决定。多机协作要留意一个坑:`synced` 是本地 tag,`/wrapup` 用 `git tag -f` 移动它后远端不会自动跟随,需 `git push --force origin synced`,否则另一台机器的 `git diff synced` 基准会停在旧位置、漏掉联动检查。

### 决策 8 · sync horizon 用 `synced` tag,不用裸 HEAD

"上次同步到哪了"这个边界,**不能**用"最近一次 commit / HEAD"。因为决策 6 允许用户随时手工 commit:一旦用户没跑 `/wrapup` 就自己 commit 了,那笔改动进了 HEAD,下次 `git diff HEAD` 看不到它 → **它的联动被永久跳过,且无任何信号**。

所以 horizon = 独立的 git tag `synced`(上次**已同步**的提交)。`/wrapup` 第 2 步用 `git diff synced`(覆盖"已 commit 未同步"+"未 commit"两类),第 5 步末尾 `git tag -f synced` 推进。手工 commit 不再隐形。

### 决策 9 · 套件版本治理:统一版本行 + CHANGELOG(由决策 24 扩展)

**做了什么**:每个机制文件(仓库级 Skill 及其 metadata、机器级安装器 Skill 与获取脚本、Claude 命令适配器、本目录三份机制文档、hooks 脚本、分发联动模板)带一行 `一致性机制 version: YYYY-MM-DD` 注释。初版把它称作套件版本:任何机制文件发生真实变化,**全部版本行一起 bump 到当天**,并在套件根 `CHANGELOG.md` 记一行。`project-consistency-installer` 以版本行机械判定目标项目副本新旧;根 `AGENTS.md` 与 `templates/AGENTS.md` 的同步纪律 marker 也随套件统一推进。决策 24 引入正式 SemVer 后,这条日期行保留为**统一文件修订标识**,继续承担混合版本和同日热修检测,不再是对外产品版本。

**为什么**:本机制以"复制"方式分发进 N 个项目。没有文件修订身份,各项目里的副本会静默漂移、且无从判定谁旧——"慢慢腐烂"恰好发生在机制自己身上。"疑似旧版"必须可机械判定(一条 grep),更新提示才不是空话。日期适合回答“这批机制文件是哪天修订的”;对外发布与兼容边界后来交给决策 24 的 SemVer。

**代价**:改机制文件多一道手续(bump 全部修订日期 + 记 CHANGELOG),靠第七节的维护清单兜住。修订标识是套件级、非单文件级——某文件"没改也被 bump"是预期行为,换来机械发现目标项目是否混装不同批次机制件的能力;正式“装的是哪版”由决策 24 的 VERSION 回答。

### 决策 10 · 出向兜底 hook:收尾提醒(纪律 → 制度)

**问题**:决策 3 的 safety net 只能回看**当前会话**的对话,而它是否被执行,完全取决于用户**记得**在会话结束前跑 `/wrapup`。忘了 → 窗口永久关闭,未落盘的 B 类事件**静默丢失**——这是机制中唯一「丢了无信号」的失败模式。

**解决**:初版用一个挂在 Claude Code `Stop` 事件(AI 每轮回答结束)上的纯 shell 脚本 `一致性机制/hooks/收尾提醒.sh`:检测「项目装了机制 + 工作区有未同步改动(`git diff synced` + 未跟踪)+ 本脏周期还没提醒过」→ 给用户弹一行提示「建议收尾跑 /wrapup」。用户在窗口还开着时跑 `/wrapup`,safety net 得以执行,对话里的决策被捞回落盘。决策 23 后续把同一脚本接入 Codex 本地客户端;决策 25 再把判断逻辑迁到跨平台 `.agents/hooks/wrapup-reminder.mjs`,原 `.sh` 降为旧接线兼容包装。

**为什么挂 Stop 不挂 SessionEnd**:SessionEnd 触发时会话已终止,既无法给 AI 喂话、也没有给用户弹消息的通道(查证于 2026-06,Claude Code v2.1.170)。「会话结束时提醒」的正确实现位置,其实是「每轮结束时 + 防唠叨门控」。

**三条红线**:
1. **只提醒,不行动**——不自动跑 /wrapup、不打断 AI(任何分支都 exit 0)、不碰 commit/push,保持「兜底不门禁」(决策 6)的气质。
2. **每个脏周期最多一次**——状态文件(/tmp,按 会话×项目 隔离)防唠叨;工作区清零(跑过 /wrapup)后自动删状态、重新武装。
3. **逻辑与接线分离**——脚本使用常见 shell 与 git 工具完成判断;`.claude/settings.json` 和 `.codex/hooks.json` 只保存宿主接线,不复制业务逻辑。

**覆盖面(诚实)**:hook 读不到对话,**不是** B 类事件探测器,只是「关门前的广播」——保证 safety net 在还能看见对话时被触发。盲区:纯讨论会话(全场零文件改动)+ AI 又恰好违纪未落盘 → 仍会丢。封死盲区需要语义判断(LLM 评估型 hook,每轮判断「有无未落盘决策」),留待将来,暂不做。

**代价**:每轮回答结束多一次毫秒级本地脚本执行;项目级 hooks 首次生效需按宿主完成信任或权限确认。

### 决策 11 · 决策记录轮转归档:工作集留 PROJECT,历史进档案

**问题**:“关键决策记录”是项目事实中唯一 append-only 的部分。无上限会让每次 `/catchup` 读取的工作集持续膨胀,但决策 3 钉死的 canonical 落点又不能丢。

**解决**:两层分工——
- **落点随职责迁移**:决策第一时间落 PROJECT 决策记录;操作性内容同时改写进 PROJECT 正文或对应领域文档。记录行只是审计线索。
- **容量上限 + 轮转**:PROJECT 只留最近 10 条;`/wrapup` 发现超限 → 提议把最老条目剪切到 `一致性机制/决策档案.md`,PROJECT 留一行指针。

**关键取舍**:档案不进 Part A、`/catchup` 不默认读取。与 git 同构:PROJECT 决策节 = 当前工作集,档案 = 历史。

**代价**:查很久以前的决策多一跳(打开档案);轮转依赖 /wrapup 跑到——条件触发,超限才有动作,平时零成本。

### 决策 12 · 安装器双形态:全局命令 + skill(行为正本位置后由决策 19 取代)

**问题**:`/引入一致性机制` 是机器级分发件(偶尔在别的项目里调一次),靠符号链接驻留 `~/.claude/commands/`。但斜杠命令靠**显式记忆**——用户得记得这个名字才用得上;且该目录一旦缺失(换机 / 清理 / 从未落机),安装器静默消失,无信号(2026-07 实测发生)。

**解决**:给安装器加一层 **skill 封装**(`一致性机制/skills/引入一致性机制/SKILL.md`,符号链接驻留 `~/.agents/skills/`):skills 按 description **语义自动触发**(「给这个项目装一致性机制」即可命中,无需记命令名)。SKILL.md 是**纯指针**——只含触发描述与「去读正本」,安装步骤的唯一正本仍是 `.claude/commands/引入一致性机制.md`;两种形态同一文件,**零双份漂移**。

**为什么不进项目**:安装器是套件的分发工具,与全局命令同级、机器级;项目里只需要它的产物(catchup/wrapup 等)。故绿地 rsync 排除它,安装器自身也不拷它。

**代价**:触发层到正本多一跳(skill 先读正本才能干活);机器级符号链接变两处,套件迁移都要重建(登记册已记)。

**后续**:这个方案解决了语义触发,但仍依赖作者机器上的绝对 checkout 路径,且把跨 Harness 安装行为正本放在 Claude 专属命令目录。决策 19 将正本迁到可由 skills.sh 分发的标准英文 Skill,全局命令降为适配器。

### 决策 13 · 套件主页与项目地图模板分离(已由决策 15 扩展)

**问题**：套件根 `README.md` 同时承担 GitHub 项目介绍和新项目地图骨架两个角色。公开展示需要解释机制、安装方式与边界；新项目需要的是带占位符的目录地图。两种内容放在同一文件中，会让项目主页残留模板占位，也会在初始化时把套件介绍复制进目标项目。

**解决**：套件根 `README.md` 只作为公开项目主页，项目地图骨架独立存放在 `templates/README.md`。绿地初始化明确排除根 README，再把模板复制为目标项目的 `README.md`；已有项目缺少 README 时，安装器也只读取该模板。

**为什么**：公开页面和分发模板的受众、生命周期不同。分开后，项目主页可以持续完善而不影响安装产物，模板也能保留必要占位符，不会降低仓库完成度。

**后续**:该决策先把公开主页与模板分开,但仍默认“README = 项目地图”。决策 15 进一步让 README 完全退出运行协议,项目地图迁入 PROJECT,`templates/README.md` 随之取消。

### 决策 14 · 套件项目大脑与新项目 CLAUDE 模板分离(同日被决策 15 取代)

**问题**:套件根 `CLAUDE.md` 原本既是新项目的分发骨架,又是 `/catchup` 必读的当前项目大脑。为了方便复制而保留的占位符,会让套件仓库自己无法记录真实背景、阶段与决策;结果是这套机制在维护自身时反而不能完整 catchup。

**解决**:根 `CLAUDE.md` 只描述套件自身,新项目骨架迁到 `templates/CLAUDE.md`。绿地初始化排除根 CLAUDE 后显式复制模板;增量安装器的新建全骨架和同步纪律注入也统一读取 `templates/CLAUDE.md`,不再把套件自身状态带进目标项目。

**为什么**:项目状态与分发模板的受众、生命周期不同。拆分后,套件可以像任何采用本机制的项目一样维护自己的阶段和决策,模板仍保持可填充、可复制;同时与决策 13 的 README 分层形成一致规则——根文件属于套件,`templates/` 属于新项目。

**后续**:这一步解决了“套件状态不能自描述”,但仍让 CLAUDE 同时承担项目事实与 Agent 指令,且 `/catchup` 会重复读取 harness 已注入的内容。决策 15 把项目事实迁到 PROJECT、指令迁到 AGENTS,CLAUDE 降为链接适配层,因此 `templates/CLAUDE.md` 不再存在。

### 决策 15 · 公开展示、项目事实与 Agent 指令三层分离

**问题**:README 会被 GitHub 默认展示,真实项目往往需要把它写成产品门面、安装/API 文档或用户指南;让它同时承担运行时项目地图会制造职责冲突。另一方面,Codex 会自动加载 AGENTS、Claude Code 会自动加载 CLAUDE,`/catchup` 再完整读取同一内容既重复消耗上下文,也可能让启动时旧版与磁盘新版同时出现。

**解决**:

- `README.md`:对外展示,可选,用户自有;不再是默认中枢或项目地图。
- `PROJECT.md`:项目事实正本,保存背景、流程、地图、阶段与近期决策;由 catchup 显式读取。
- `AGENTS.md`:Agent 工作规则与同步纪律的唯一实体正本;由 Codex 等 harness 自动加载。
- `CLAUDE.md`:Claude Code 适配器;决策 25 后统一只含 `@AGENTS.md`,导入同一规则正本而不复制内容。
- catchup:不再读取 AGENTS / CLAUDE 正文,只验证适配器形态,再读取 PROJECT、Git 与焦点文件。

**为什么**:三个文件分别服务外部读者、项目运行和 Agent harness,生命周期与更新触发都不同。拆开后 README 可自由重写或不存在,Agent 指令不会重复进入上下文,项目事实也不绑定某个厂商文件名。

**代价**:需要迁移旧项目中混在 CLAUDE / AGENTS / README 的内容。初版依赖 Git checkout 保留相对符号链接,只覆盖 macOS/Linux;该平台限制已由决策 25 的通用导入适配器消除。

### 决策 16 · 套件真实联动规则与分发骨架分离

**问题**:`一致性机制/文件联动目录.md` 原本既要描述套件自身的稳定联动,又会被复制到所有目标项目。写入套件专属规则会污染分发骨架;保持通用占位又让套件无法用自己的机制维护自己。

**解决**:根 `一致性机制/文件联动目录.md` 只保存套件真实规则;通用骨架迁到 `templates/一致性机制/文件联动目录.md`。绿地初始化与增量安装器只复制模板,永不复制套件实况。

**代价**:新增一个必须防混用的模板来源;因此套件真实联动目录增加固定规则,要求模板变化时同步检查初始化、安装器、项目地图与公开说明。

### 决策 17 · 出向命令统一为 `/wrapup`(行为正本位置后由决策 18 取代)

**问题**:入向命令已经使用英文 `/catchup`,出向命令仍使用中文名称,分发时形成混合命名;直接改成 `/sync` 又会暗示包含远端 `git push`,与“只做本地联动、commit 和 `synced` horizon”的真实边界不符。

**解决**:出向命令统一为 `/wrapup`,与 `/catchup` 形成“会话开始恢复 / 会话结束收尾”的语义配对。当时文件正本改为 `.claude/commands/wrapup.md`;决策 18 随后把行为正本迁入仓库级 Skill,这里只保留命名结论。“同步纪律”“同步边界”仍作为机制概念保留。

**升级边界**:旧项目可能仍有旧版中文命令文件。安装器必须先比较内容:未定制时经用户确认迁移并移除旧入口;存在项目定制时列出差异并人工合并,不得静默覆盖或让两个出向命令长期并存。

### 决策 18 · catchup / wrapup 以仓库级 Skill 为行为正本

**问题**:`.claude/commands/` 是 Claude Code 专属入口。把完整流程放在那里,Codex 和其他支持 Agent Skills 的 Harness 只能靠自然语言间接读取,且为不同宿主再复制流程会制造多份正本。

**解决**:把完整 catchup / wrapup 流程迁入 `.agents/skills/catchup/` 与 `.agents/skills/wrapup/`。Codex 从仓库根直接发现 Skill,可用 `$catchup` / `$wrapup` 或语义触发;Claude Code 的 `/catchup` / `/wrapup` 文件只负责读取对应 `SKILL.md`,不再保存步骤正文。

**为什么**:行为正本随仓库分发,入口按 Harness 适配。支持 Agent Skills 的宿主直接复用;只支持项目指令的宿主仍可由 AGENTS 引导读取 Skill;Claude Code 保留用户熟悉的斜杠体验。

**代价**:不同 Harness 的显式调用符号并不统一,且 Stop hook 仍需宿主接线。旧项目升级时还必须把命令文件中的定制安全迁入 Skill,不能直接用薄适配器覆盖。

### 决策 19 · 安装器以 skills.sh Skill 分发,按需从 GitHub bootstrap

**问题**:旧安装器 Skill 只是一个指向本机 `~/Developer/项目一致性机制` 的中文名封装。新机器必须先知道仓库地址、手动 clone、再建立符号链接;安装器正本仍在 `.claude/commands/`,与决策 18 的“Skill 正本、宿主薄适配”不一致。

**解决**:把完整安装工作流迁到 `skills/project-consistency-installer/`,采用 skills.sh 可发现的英文小写标识。用户只需从 GitHub 全局安装这个 Skill;运行时优先使用可信本地 checkout,不存在则由随附 `fetch-kit.sh` 把规范仓库获取到机器缓存,验证 remote、干净状态、ref、commit 与必要文件后再开始目标项目迁移。Claude `/引入一致性机制` 降为定位该 Skill 的薄适配器。

**两阶段边界**:skills.sh 只分发机器级引导器,不负责 PROJECT、AGENTS、hooks 等非 Skill 文件。引导器取得整套 GitHub 源后,才把 catchup / wrapup 仓库级 Skill 与其他机制件增量写入目标项目。下载脚本只动机器缓存,项目写入仍由 Agent 展示计划并等待确认。

**安全与版本取舍**:默认 ref 暂为 `main`,每次报告实际 commit;用户可显式指定 tag 或 commit。缓存 remote 不符、有本地改动或文件不完整时立即停止,不强制清理。正式发布稳定后应以套件 release tag 作为推荐 ref,降低可变分支带来的供应链漂移。

**代价**:首次使用依赖 Node.js、skills CLI、Git 和网络;skills.sh 是第三方分发入口,并不替代 GitHub 作为源码正本。离线环境仍需本地 checkout 或预热缓存。

**后续**:决策 22 完成正式发布收敛:安装器不再默认 clone `main`,而是获取带来源元数据和双层校验的干净 GitHub Release;本地源码 checkout 只保留为用户明确提供的开发来源。

### 决策 20 · 自然语言意图作为跨 Harness 的统一用户入口

**问题**:各个 Harness 的显式 Skill 调用方式不同。把 Codex 的 `$project-consistency-installer` 写成默认入口,会让人误以为 Codex 是主要宿主;Claude Code 有自己的斜杠适配器,其他 Harness 也可能使用 Skill 选择器或不同语法。

**解决**:面向用户统一使用“给这个项目引入一致性机制”这句自然语言意图。`project-consistency-installer` 保留为稳定的 Skill 标识,供 Harness 做语义匹配或显式选择。Codex 的 `$project-consistency-installer`、Claude Code 本地开发适配器的 `/引入一致性机制`,以及其他 Harness 的选择入口都属于宿主适配层。

**边界**:自然语言是统一的用户契约,不是新的调用协议。Harness 若不支持隐式 Skill 匹配,用户仍需通过它提供的显式入口选择 `project-consistency-installer`;安装行为始终由同一份 `SKILL.md` 定义。

### 决策 21 · 决策档案实况与分发模板分离

**问题**:套件根 `一致性机制/决策档案.md` 起初是空文件,安装器与绿地初始化曾直接把它复制到目标项目。套件自身第一次轮转历史决策后,这条路径会把套件决策 9 一并带进所有新项目,直到端到端安装测试才暴露。

**解决**:套件根档案只保存套件自身历史;新增 `templates/一致性机制/决策档案.md` 作为无项目记录的分发骨架。安装器和绿地初始化只从模板创建新档案,并继续对目标项目已有档案执行整文件跳过,不合并、不覆盖。为修复已安装项目,安装器只把已知泄漏记录的完整原行作为迁移签名:命中后展示上下文,经用户确认才删除精确行,其余项目内容不动。

同日热修可能与旧副本共享 `YYYY-MM-DD` 版本行,所以安装器不能把“版本相同”当成“内容相同”;仍须比较实际内容,区分规范热修与项目定制后再提出更新。

**为什么**:决策档案和联动目录一样包含项目实况,不能因为文件最初为空就把实况文件兼作模板。模板必须在套件产生真实数据后仍保持项目无关。

**代价**:分发链路多维护一个模板来源和一组窄迁移签名;GitHub 获取校验、初始化复制和安装器升级规则必须同时验证模板存在且不含套件决策,同版本更新也多一次内容比较。

### 决策 22 · 源码自举状态与云端分发产物分离

**问题**:源码仓库为了用本机制维护自己,必须在根保留 PROJECT、AGENTS、CLAUDE 链接、真实联动目录和真实决策档案。这些文件作为源码协作状态合理,但 GitHub checkout 同时被安装器当作完整分发源时,源码面与产品发布面混在一起;每新增一种套件实况,都要依赖下游排除规则防泄漏。

**解决**:建立三层边界:

1. `main` 是源码与自举面,完整保留套件自己的运行状态;
2. `distribution/manifest.txt` 逐文件声明可发布产品,`scripts/build-distribution.sh` 只复制白名单并生成来源元数据、内部逐文件 SHA-256、`tar.gz` 与外层校验值;
3. `.github/workflows/distribution.yml` 在普通变更上验证构建,只在 `v*` 标签上用最小 `contents: write` 权限创建 GitHub Release;
4. `fetch-kit.sh` 默认下载 latest 或指定版本的干净 Release,校验外层压缩包、内部文件清单、规范来源和 source commit 后才交给安装器。校验失败不得静默退回源码 clone;
5. 目标项目仍由安装器或绿地初始化从干净源中的 templates 与通用机制件生成自己的 PROJECT、AGENTS、联动规则和决策档案。

**为什么是白名单**:黑名单只能挡住已经知道的套件状态,未来新增文件时默认会泄漏;逐文件白名单让新产品文件必须经过显式评审才能进入发布面。源码仓库因此可以继续 dogfood,而下载产物保持项目无关。

**完整性边界**:GitHub Release 的压缩包 `.sha256` 负责传输完整性,包内 `DISTRIBUTION-MANIFEST.sha256` 负责缓存与逐文件完整性,`DISTRIBUTION-METADATA.txt` 把产物绑定到规范仓库、release ref 和 40 位 source commit。它们提升可审计性,但不替代 GitHub 账号、Release 权限与 HTTPS 本身的信任边界。

**代价**:发布过程新增白名单维护、构建验证和版本标签;机器首次安装依赖 curl、tar 与 SHA-256 工具。源码 main 仍会公开自举文件——干净承诺属于 Release 资产和安装结果,不是源码树的视觉隐藏。

### 决策 23 · 收尾提醒采用共享脚本 + 宿主接线

**问题**:catchup / wrapup 已通过仓库级 Skill 支持 Codex,收尾提醒却只有 Claude Code 的 `.claude/settings.json` 接线。Codex 用户可以主动运行 `$wrapup`,但忘记收尾时没有同等兜底;为 Codex 再写一份检测脚本又会制造双份逻辑。

**解决**:v1.1.0 让 `一致性机制/hooks/收尾提醒.sh` 作为唯一逻辑正本,从当前会话目录经 git 定位仓库根,并按宿主显示 `/wrapup` 或 `$wrapup`。Claude Code 保留 `.claude/settings.json`;Codex 本地客户端新增 `.codex/hooks.json`,两者都挂 `Stop`。Codex 输出只使用 `systemMessage`,不返回会自动续跑的 `decision: "block"`,因此仍然只提醒、不行动。决策 25 将同一职责迁到跨平台 Node 脚本,没有改变本决策的“单逻辑正本 + 宿主薄接线”。

**为什么用 Stop**:Codex 的 `Stop` 在主 Agent 准备结束当前轮次时运行,能及时显示提醒;`SessionEnd` 要等会话关闭、归档或闲置后才运行,输出也不能继续线程。选择 `Stop` 与现有防唠叨状态机配合,能在对话仍可回看时提醒一次。行为依据 [OpenAI Codex Hooks 文档](https://learn.chatgpt.com/docs/hooks),本机 `codex-cli 0.148.0-alpha.15` 已将 hooks 标为 stable。

**配置与信任边界**:Codex 同一项目层同时存在 `hooks.json` 与 `config.toml` inline hooks 时会合并并警告,所以安装器必须先探测现状:默认创建 `.codex/hooks.json`,已有 JSON 时增量合并,已有 inline TOML 时只合并 TOML,两者并存则交给用户选择收敛方向。项目命令 hook 需要用户审查和信任;安装器只能报告“待信任”,不能把配置写入等同于已经生效。

**范围**:v1.1.0 先覆盖支持项目 hooks 的 Codex 本地客户端与 macOS/Linux bash 路径,不承诺 Codex Cloud;Windows `commandWindows` 当时留待验证。决策 25 已补齐原生 Windows 接线与真机验证。其他 Harness 仍只有在提供等价生命周期 hook 后才增加适配器。

### 决策 24 · 正式版本使用 SemVer,日期降为文件修订标识

**问题**:统一日期版本行能发现复制文件漂移,但 GitHub Release 已使用 `v1.0.0` 标签,分发元数据又只记录 ref 与 commit。用户、安装器和发布页同时看到日期、tag、commit,却没有一个明确的“当前 Kit 是哪一版”;机器级安装器单独由 skills.sh 分发时也无法直观报告它属于哪一版套件。

**解决**:`一致性机制/VERSION` 保存唯一正式 SemVer,整套产品——安装器、catchup、wrapup、hooks、模板与宿主适配器——锁步发版,暂不维护组件独立版本。安装器 `SKILL.md` 的 `metadata.version` 镜像该值,仅用于安装器单独落机后的机器可读身份;构建验证必须保证二者一致。日期版本行继续全套统一推进,语义改为文件修订日期;40 位 source commit 继续提供不可歧义的精确来源。

**发布门禁与 schema 兼容**:分发元数据继续使用 schema 1,以向后兼容字段扩展的方式加入 `kit_version` 与 `mechanism_revision`;v1.0.0 的旧安装器会忽略新增字段并继续接受 v1.1.0 latest,新版安装器则区分 versioned schema 1 与缺少新字段的 legacy schema 1。只有包结构或校验语义发生旧读取器无法安全忽略的破坏变化时才升级 schema。若构建来源是 `v*` tag,tag 必须精确等于 `v<VERSION>`;GitHub Actions 的 tag 发布因此会在版本正本、Skill metadata、tag 或产物元数据任一漂移时失败。legacy 包仍按其历史最低文件集合验证,避免新安装器无法固定或离线使用旧版本。

**目标项目身份**:安装时把 `一致性机制/VERSION` 随机制件写入目标项目。安装器先报告“安装器版本 / 来源 Kit 版本 / 目标现有版本 / 计划动作”,完成后再报告修订日期、ref 与 commit。缺少 VERSION 的旧项目不猜造 SemVer,标为“旧版或未标记”,再用日期行和实际 diff 辅助迁移。

**版本推进**:破坏兼容边界时升 major,新增兼容能力时升 minor,兼容修复时升 patch;仅修改项目自身运行状态、不改变分发产品时不升。日期修订标识仍在任何机制件真实变化时统一推进,同一天的热修通过实际 diff 与 source commit 区分。

### 决策 25 · Windows 使用通用导入、跨平台 hook 与双层验证

**问题**:v1.1.0 的两个关键路径仍依赖 Unix 语义:`CLAUDE.md -> AGENTS.md` 在 Windows 未启用 Developer Mode / 管理员权限时可能被 Git checkout 成普通指针文本;Stop hook 与 Release 获取脚本都直接调用 bash。结果是仓库文件看似存在,Claude Code 却未必加载 AGENTS,原生 PowerShell 环境也无法稳定执行 hook 或安装器。同时 GitHub Actions 仍使用基于 Node 20 的旧 checkout Action,开始产生弃用提醒。

**解决**:

1. `CLAUDE.md` 在所有平台统一为普通文件且只含 `@AGENTS.md`。这是 Claude Code 官方支持的项目内导入,仍由 AGENTS 承担唯一规则正本,并彻底移除 symlink 权限与 checkout 差异;
2. Stop 判断逻辑迁到全 ASCII 固定路径 `.agents/hooks/wrapup-reminder.mjs`,Claude Code 用 exec-form `command + args` 绕开 shell差异,Codex 在 Unix 使用 `command`、Windows 使用 `commandWindows`;旧 `.sh` 只转发到 Node 正本。ASCII 路径避免 PowerShell 5.1 / shell 代码页把中文命令路径静默改写;
3. Windows 安装入口 `fetch-kit.ps1` 只负责定位 Git for Windows 的 Bash、转换路径并调用 `fetch-kit.sh`,不复制下载与校验逻辑;
4. CI 升级到 `actions/checkout@v6`,Linux 与 `windows-latest` 都运行 Stop 状态机测试,Windows 额外构建并经 PowerShell 入口验证干净分发包;
5. 真实 Windows 主机再做一轮 PowerShell 5.1、Git for Windows、Claude Code 与 Codex CLI 联调。CI 保证干净环境可重复,真机暴露实际安装、PATH 与宿主差异;报告必须分别给出脚本 / 适配器直测和宿主端到端结果,不得用前者代替后者。

**为什么不是两份 hook**:PowerShell 与 Bash 各维护一份状态机,会让文件计数、防重复和输出协议逐步漂移。Node 已是 skills.sh 安装链路的既有依赖,用一个无 shell 的跨平台脚本能保住单一行为正本;PowerShell 只留在宿主接线和 Windows 获取入口。

**首轮真机结论与边界**:原生 Windows 需要 Git、Node.js 和 Git for Windows 自带的 Bash(获取脚本复用它);hook 本身只需要 Git + Node。Windows 10 + PowerShell 5.1 真机已通过获取、分发校验、状态机和 `commandWindows` 精确命令直测。当时 Codex 0.148.0 交互界面能识别并显示 Stop hook,却没有提醒输出,因而初步归因为宿主未执行命令;决策 26 的桌面端再验证证明这个归因不准确,宿主已经调度命令,真正失效发生在内联 PowerShell 的二次解析。Codex 项目 hook 仍需用户信任;Codex Cloud 仍不在范围。

**v1.2.1 发布修正**:真实 Windows 的包内验证通过后,`v1.2.0` 标签工作流进一步暴露了源码 checkout 差异:Git for Windows 的 `core.autocrlf=true` 会让 `distribution/manifest.txt` 每条记录带 `\r`,Bash 若直接把整行拼成路径就会误报首个文件缺失。构建与校验脚本因此在白名单读取边界剥离 `\r`;不强制整仓库或目标项目统一换行。已经公开的失败标签不移动,由补丁版本 v1.2.1 承担修复发布。

### 决策 26 · Windows Codex 用 PowerShell 薄适配器隔离宿主解析

**问题**:v1.2.1 的 `commandWindows` 把一段含 `$root` 的 PowerShell 脚本放进双引号,再启动第二个 `powershell.exe -Command`。Codex Windows 会话本身已经由 PowerShell 执行 hook 命令,所以外层会在内层进程启动前就把 `$root` 展开为空;最终 Node 收到错误路径。单独复制 `commandWindows` 直测只有一层解析,因而会假通过;这也是首轮误判为宿主上游缺陷的根因。

**解决**:v1.2.2 新增 `.agents/hooks/wrapup-reminder.ps1`。`commandWindows` 只用不含变量的表达式从 git 根定位这个文件,然后以 `-File` 启动;适配器在文件内完成一次解析,只定位 Node 正本、转发 stdin 并保持失败开放。为避免 Windows PowerShell 5.1 在子进程与外层会话间用本地代码页重新解码 UTF-8,Node 把非 ASCII 字符以 JSON 标准 `\uXXXX` 形式输出;宿主 JSON 解析后仍得到原始中文与 emoji。文件计数、会话防重和输出协议仍只在 `.mjs` 维护,没有形成第二份 Hook 逻辑。

**验证约束**:Windows 自动化不再只直测内层命令,而是从子目录启动一个外层 PowerShell,执行完整 `commandWindows`,通过 `.ps1` 向 Node 传入 Stop JSON,并断言 `$wrapup` 的 `systemMessage`。真机报告仍必须区分“脚本直测”与“Codex 桌面端端到端”;项目与变更后 Hook 命令的用户信任边界不变。

**真机结论**:Windows 10 + Windows PowerShell 5.1 候选包已通过分发反向校验、Node 状态机、外层 Shell 整链路与测试仓库精确命令直测。Codex 0.148.0 桌面端在用户信任变更后的项目 Hook 后,真实 Stop 事件以项目 Hook 通知浮层正确显示“5 个文件”与 `$wrapup`;因此 Windows Codex 桌面端适配在 v1.2.2 候选范围内完成端到端闭环。

## 四、文件类型与 git 兼容度速查

| 类型 | 例子 | git diff | 处理 |
|------|------|---------|------|
| 文本 | .md .txt .json .yaml .csv .html .css .js | 🟢 完美 | 普通 git |
| 矢量 | .svg | 🟢 是 XML | 普通 git |
| 栅格图 | .png .jpg .webp .heic | 🔴 二进制 | Git LFS(默认) |
| 设计源 | .psd .ai .indd | 🔴 + 通常很大 | gitignore + manifest |
| Office/PDF | .docx .xlsx .pdf | 🔴 二进制 | gitignore + .md 摘要 |
| 字体/媒体 | .ttf .mp4 .mp3 | 🔴 二进制 | gitignore + manifest |

**核心原则**:所有"决策、文字、规范、记录"都用 .md;需要版本史的栅格图走 LFS;其余二进制当"附件",由 manifest 翻译。

## 五、项目套用本机制后的结构

一个采用了本机制的项目,大致长这样(`<...>` 是项目自己的内容):

```
<某项目>/
├── .git/                     版本控制本体(事件源)
├── .gitignore                二进制排除规则(可按项目改)
├── .gitattributes            选择性 LFS 规则(可按项目改/删)
├── README.md                 对外说明(可选,不属于核心协议)
├── PROJECT.md                项目事实、地图、阶段与近期决策 ⭐
├── AGENTS.md                 Agent 工作规则唯一实体正本 ⭐
├── CLAUDE.md                 只含 @AGENTS.md 的 Claude Code 导入适配
├── .agents/skills/           跨 Harness 工作流正本 ⭐
│   ├── catchup/
│   │   ├── SKILL.md
│   │   └── agents/openai.yaml
│   └── wrapup/
│       ├── SKILL.md
│       └── agents/openai.yaml
├── .codex/
│   └── hooks.json            Codex 本地 Stop hook 接线
├── 一致性机制/                ★ 本机制:文档 + 规则 + hook
│   ├── README.md             机制索引 + 钉在别处的文件登记册
│   ├── 机制设计说明.md         ← 本文件
│   ├── 文件联动目录.md         ⭐ 联动规则(双层模型,wrapup 读取)
│   ├── 决策档案.md             决策记录历史档案(规则 6 轮转进来)
│   ├── LICENSE.project-consistency-kit  套件许可副本
│   └── hooks/
│       └── 收尾提醒.sh         旧 Unix 接线兼容包装
├── .agents/hooks/
│   ├── wrapup-reminder.mjs    跨平台出向兜底 hook 正本(决策 10/25)
│   └── wrapup-reminder.ps1    Windows Codex 薄适配器(决策 26)
├── .claude/
│   ├── settings.json         hook 接线(Stop → 收尾提醒)
│   └── commands/
│       ├── catchup.md        Claude Code 入向薄适配器
│       └── wrapup.md         Claude Code 出向薄适配器
└── <项目自己的目录>            正文/代码/素材/产物……
```

> 注意:`PROJECT.md`、`AGENTS.md`、`CLAUDE.md` 导入适配器、`.agents/skills/`、`.claude/commands/`、`.claude/settings.json`、`.codex/hooks.json`、`.gitignore` 与 `.gitattributes` 因职责或工具要求必须在仓库根 / 固定位置。登记册见 `一致性机制/README.md`。

## 六、给接手 AI 的建议

接手一个用了本机制的项目,按此顺序读:

1. 确认 harness 已自动加载 **`AGENTS.md`** 或经 **`CLAUDE.md`** 导入的同一内容;不要再显式读取一遍
2. 执行 **catchup**(Codex: `$catchup`;Claude Code: `/catchup`)——读取 `PROJECT.md`、Git 与当前焦点
3. 按需读**本文件**理解机制动机
4. 按需读 `一致性机制/文件联动目录.md` 理解具体联动
5. README 仅在需要了解对外契约时阅读

接手第一件该做的事:执行 catchup 确认理解准确。

若对机制设计有疑问或觉得有更好方案,**先和用户讨论,别直接动架构**——每个看似奇怪的选择背后都有具体权衡,本文第三节就是解释这些"为什么"的。

## 七、本机制自身的维护

- **改任何机制文件(仓库级工作流 Skill / 机器级安装器 Skill与跨平台获取入口 / Claude 命令适配器 / Codex hook 适配器 / 本目录三份机制文档 / hooks 脚本 / 分发模板)= 一次套件发版**:先按兼容性判断 `一致性机制/VERSION` 的 major / minor / patch,同步安装器 metadata,再把全部 `一致性机制 version:` 行以及根 `AGENTS.md`、`templates/AGENTS.md` 的修订日期推进到当天 + 套件根 `CHANGELOG.md` 记入对应版本(决策 9/24)。
- 机制发生**真实变化**时(不只规则微调),更新本文件。
- 某个决策被推翻时,**保留原描述 + 标注"已废弃"**,不要直接删——留演进路径给接手者看。
- 改本机制的文件也走 wrapup:它会按套件真实 `文件联动目录.md` 检查 PROJECT、AGENTS、公开 README、模板、初始化、安装器与 CHANGELOG,再经确认 commit、推进 `synced`。
